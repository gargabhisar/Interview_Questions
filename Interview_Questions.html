MongoDB vs SQL Databases

SQL databases are relational, schema-first systems that store data in tables with enforced relationships and ACID transactions. MongoDB is a document-oriented NoSQL database that stores flexible JSON-like BSON documents in collections, optimized for horizontal scaling and rapid schema evolution.

On SQL Server you also tune parallelism with MAXDOP (maximum degree of parallelism), which limits how many CPUs a single query may use—separate from the SQL vs document-store choice but important for relational performance.

AspectSQLMongoDB
Data modelTables, rows, columnsCollections, documents
SchemaFixed, enforcedFlexible, optional
ScalingMostly verticalHorizontal sharding
JoinsNative JOINsEmbedding or $lookup
-- SQL: normalized order query
SELECT o.OrderId, c.Name
FROM Orders o
JOIN Customers c ON o.CustomerId = c.Id;

-- MongoDB: embedded or lookup
db.orders.aggregate([
  { $lookup: { from: "customers", localField: "customerId",
      foreignField: "_id", as: "customer" } }
]);

Key Points

  • Choose SQL when you need strong consistency, complex joins, and reporting.
  • Choose MongoDB for flexible schemas, high write throughput, and document-centric apps.
  • Many teams use both: SQL for transactional core, MongoDB for logs or content.

Interview Answer

SQL is relational and ACID-focused with strict schemas; MongoDB is document-based and schema-flexible, better for scale-out and evolving data shapes. I pick based on consistency needs, query patterns, and team expertise—not hype.

MongoDB Queries with C# (.NET Driver)

Official package: MongoDB.Driver. Install via NuGet or dotnet add package MongoDB.Driver.

1. Model class

using MongoDB.Bson;
using MongoDB.Bson.Serialization.Attributes;

public class Employee
{
    [BsonId]
    [BsonRepresentation(BsonType.ObjectId)]
    public string? Id { get; set; }

    public string Name { get; set; } = "";
    public int Age { get; set; }
    public string Department { get; set; } = "";

[BsonId] maps to MongoDB _id. Omit Id on insert and the driver generates an ObjectId.

Monolithic vs Microservices Architecture

A monolith is a single deployable application containing all modules—UI, business logic, and data access—sharing one process and often one database. Microservices split the system into independently deployable services, each owning a bounded context and communicating over HTTP or messaging.

Monoliths are simpler to develop and debug early on. Microservices improve scalability and team autonomy at the cost of distributed complexity—network failures, observability, and deployment pipelines multiply.

AspectMonolithMicroservices
DeploymentSingle unitIndependent services
ComplexityLower initiallyHigher operational overhead
ScalingScale entire appScale hot services
Best whenSmall teams, MVPsLarge domains, many teams

Key Points

  • Start monolith unless clear boundaries justify splitting.
  • Microservices need strong DevOps and observability.
  • Domain boundaries matter more than technology choice.

Interview Answer

A monolith is one deployable app that is easy to build initially but harder to scale independently. Microservices decompose by business capability for independent deployment and scaling, but add network, consistency, and operations complexity. I choose based on team size, domain clarity, and scaling needs—not hype.

Multiple catch Blocks in try-catch

C# evaluates catch clauses top to bottom; the first matching exception type handles it. Specific exceptions must come before general ones. Only one catch runs per thrown exception.

try
{
    var json = File.ReadAllText(path);
    var data = JsonSerializer.Deserialize<Order>(json);
}
catch (JsonException ex)
{
    _logger.LogWarning(ex, "Invalid JSON");
}
catch (FileNotFoundException ex)
{
    _logger.LogError(ex, "File missing");
}
catch (IOException ex) when (ex.HResult == -2147024784)
{
    // filter clause — disk full
}
catch (Exception ex)
{
    _logger.LogCritical(ex, "Unexpected failure");
    throw; // preserve stack trace
}

Key Points

  • Order: most specific → least specific; Exception last.
  • catch when filters on type plus condition without catching base first incorrectly.
  • Use throw; not throw ex; to rethrow preserving stack.
  • finally runs regardless—use for cleanup (Dispose patterns).

Interview Answer

Multiple catch blocks let you handle different failure types differently. Place specific handlers first, optionally use exception filters with when, and use a general catch only for logging before rethrow or graceful degradation.

Database Normalization & Its Forms (1NF, 2NF, 3NF)

Normalization is the process of organizing relational tables to reduce redundancy and prevent data anomalies. Each normal form adds a rule that removes a specific kind of bad dependency.

Why normalize?

Without normalization, the same fact is stored in multiple rows. That causes:

AnomalyProblemExample
InsertCannot add data without unrelated dataCannot add a new product until someone orders it
UpdateSame fact updated in many placesCustomer city changed in 50 order rows—some missed → inconsistent data
DeleteRemoving one row loses unrelated dataDeleting last order removes customer address entirely

Quick reference

FormRule (simple)Fixes
1NFAtomic values; no repeating groupsMulti-valued columns, nested lists in one cell
2NF1NF + no partial dependency on a composite keyNon-key column depends on only part of the key
3NF2NF + no transitive dependencyNon-key column depends on another non-key column

1NF — First Normal Form

Rule: Each column holds a single atomic value; each row is unique; no repeating groups (arrays/lists in one column).

Violates 1NF:

StudentCourses
--------------
StudentId | Name  | Courses
1         | Alice | Math, Physics, Chemistry   -- multiple values in one cell

In 1NF: one course per row (or separate Courses table).

StudentCourses
--------------
StudentId | Name  | Course
1         | Alice | Math
1         | Alice | Physics
1         | Alice | Chemistry

2NF — Second Normal Form

Rule: Table is in 1NF, and every non-key column depends on the whole primary key—not just part of it.

Only applies when the primary key is composite (multiple columns).

Partial dependency example:

OrderLine(OrderId, ProductId, ProductName, Qty, UnitPrice)
PK = (OrderId, ProductId)

ProductName depends only on ProductId  -- partial dependency (not on full PK)
Qty depends on full PK (OrderId + ProductId) -- OK

Fix (2NF): move ProductName to Products table.

Products(ProductId, ProductName)
OrderLine(OrderId, ProductId, Qty, UnitPrice)

3NF — Third Normal Form

Rule: Table is in 2NF, and no non-key column depends on another non-key column (transitive dependency).

Transitive dependency example:

Orders(OrderId, CustomerId, CustomerName, CustomerCity, OrderDate)
PK = OrderId

CustomerId → CustomerName, CustomerCity   -- non-key depends on non-key

If you know CustomerId, you know Name and City—those belong in Customers, not repeated on every order.

Fix (3NF):

Customers(CustomerId, CustomerName, CustomerCity)
Products(ProductId, ProductName)
Orders(OrderId, CustomerId, ProductId, Qty, OrderDate)

Walking through 1NF → 3NF (one example)

-- UNNORMALIZED (violates 1NF, 2NF, 3NF):
Orders(OrderId, CustomerName, CustomerCity, Product, Qty)

Problems:
- CustomerName/City repeat on every order (update/delete anomalies)
- Product name mixed with order facts (partial/transitive issues if composite keys exist)

-- AFTER 3NF:
Customers(CustomerId, Name, City)
Products(ProductId, Name)
Orders(OrderId, CustomerId, ProductId, Qty)

Functional dependency (interview vocabulary)

  • X → Y means: if you know X, Y is uniquely determined.
  • 2NF removes partial dependencies: non-key attribute → part of composite key only.
  • 3NF removes transitive dependencies: non-key → non-key.

When not to over-normalize

  • Many joins on hot read paths can hurt performance.
  • Reporting/data warehouse layers often denormalize intentionally (star schema).
  • Denormalize only after measuring—keep OLTP core normalized.

Interview Answer

Normalization removes redundancy and insert/update/delete anomalies by splitting tables into normal forms. 1NF ensures atomic values and no repeating groups. 2NF removes partial dependencies on composite keys. 3NF removes transitive dependencies where a non-key column depends on another non-key column. In OLTP I design to 3NF, then denormalize selectively only when profiling shows a real read bottleneck.

Boyce-Codd Normal Form (BCNF)

BCNF is a stricter form of 3NF: every determinant must be a candidate key. A table is in BCNF when for every functional dependency X → Y, X is a superkey. It eliminates anomalies 3NF might still allow when multiple overlapping candidate keys exist.

When a non-key attribute determines another non-key attribute, decompose into separate tables while keeping joins lossless and preserving dependencies where possible.

-- Violates BCNF (Teacher → Room, but Teacher is not a key):
Enrollment(Student, Course, Teacher, Room)

-- Fix: separate Teacher → Room dependency
TeacherRoom(Teacher, Room)
Enrollment(Student, Course, Teacher)

Key Points

  • BCNF ⊂ 3NF; all BCNF tables are 3NF, not vice versa.
  • Violations occur when non-key attributes determine other non-key attributes.
  • Decomposition must be lossless and preserve dependencies where possible.

Interview Answer

BCNF requires every determinant to be a candidate key. If Teacher determines Room but Teacher isn't a key, I decompose into separate tables to remove the anomaly while keeping joins lossless.

Database Indexes

Indexes are auxiliary data structures (typically B-trees) that speed up data retrieval by avoiding full table scans. They trade faster reads for extra storage and slower writes due to index maintenance.

Design indexes around real query patterns—filters, joins, ORDER BY, and GROUP BY—and validate with execution plans rather than indexing every column.

-- Clustered index on primary key (default in SQL Server)
CREATE CLUSTERED INDEX IX_Emp_Id ON Employees(EmployeeId);

-- Nonclustered index for frequent filter
CREATE NONCLUSTERED INDEX IX_Emp_Dept
ON Employees(DepartmentId) INCLUDE (LastName, Salary);
ProsCons
Faster SELECT/WHERE/JOINSlower INSERT/UPDATE/DELETE
Enforces uniqueness (unique index)Extra disk and memory

Key Points

  • Index columns used in WHERE, JOIN, ORDER BY, and GROUP BY.
  • Too many indexes hurt write-heavy workloads.
  • Use covering indexes (INCLUDE) to avoid key lookups.

Interview Answer

Indexes accelerate lookups like a book index but slow writes. I index selective, frequently queried columns, verify with execution plans, and avoid over-indexing OLTP tables.

Clustered vs Non-Clustered Indexes

A clustered index defines the physical sort order of table rows—there can be only one per table. A non-clustered index is a separate structure with pointers (or row locators) back to the data.

Range scans on the clustered key are very efficient; non-clustered indexes may require key lookups when columns aren't covered.

ClusteredNon-Clustered
One per tableMany allowed
Data stored in index orderSeparate structure + lookup
Default on PRIMARY KEYLeaf points to clustered key or RID
CREATE TABLE Employees (
  EmployeeId INT PRIMARY KEY,  -- clustered by default
  DeptId INT,
  Name NVARCHAR(100)
);
CREATE NONCLUSTERED INDEX IX_Dept ON Employees(DeptId);

Key Points

  • Range scans on clustered key are very efficient.
  • Non-clustered indexes may require key lookups (bookmark/RID).
  • Choose clustered key on narrow, ever-increasing column (e.g., identity).

Interview Answer

Clustered index sorts the table physically—one per table. Non-clustered indexes are separate lookup structures. I put the clustered index on the most common range-scan column, usually the PK.

SQL Execution Plans

An execution plan shows how the optimizer retrieves data: scan vs seek, join algorithms, sort/hash operations, and estimated vs actual row counts. Reading plans is essential for performance tuning.

Compare estimated vs actual rows; large gaps often mean stale statistics or parameter sniffing issues.

SET STATISTICS IO ON;
SET STATISTICS TIME ON;

SELECT e.Name, d.DeptName
FROM Employees e
INNER JOIN Departments d ON e.DeptId = d.DeptId
WHERE e.Salary > 80000;

-- View plan in SSMS: Ctrl+M or SET SHOWPLAN_ALL ON;

Key Points

  • Look for table/index scans on large tables—often fixable with indexes.
  • Compare estimated vs actual rows; big gaps suggest stale statistics.
  • Watch for implicit conversions, key lookups, and expensive sorts.

Interview Answer

I use execution plans to see whether SQL Server scans or seeks, which joins it picks, and where cost concentrates. Red flags are scans on big tables, bad cardinality estimates, and missing indexes.

Constraints in SQL

Constraints are rules on tables or columns that the database enforces on INSERT/UPDATE/DELETE. They keep data valid and support ACID Consistency—invalid rows are rejected before they are stored.

ConstraintPurpose
PRIMARY KEYUniquely identifies each row; NOT NULL; one per table (typically)
FOREIGN KEYLinks to parent table; prevents orphan rows (referential integrity)
UNIQUENo duplicates in column(s); allows one NULL per column in SQL Server
CHECKBoolean condition must be true (e.g. Age >= 18)
NOT NULLColumn cannot store NULL
DEFAULTValue used when INSERT omits the column
CREATE TABLE Orders (
    OrderId     INT NOT NULL PRIMARY KEY,
    CustomerId  INT NOT NULL,
    OrderDate   DATE NOT NULL DEFAULT GETDATE(),
    Status      VARCHAR(20) NOT NULL
        CONSTRAINT CK_Orders_Status
        CHECK (Status IN ('Pending','Shipped','Cancelled')),
    CONSTRAINT FK_Orders_Customers
        FOREIGN KEY (CustomerId) REFERENCES Customers(CustomerId)
);

CREATE TABLE Customers (
    CustomerId INT PRIMARY KEY,
    Email      NVARCHAR(256) NOT NULL UNIQUE
);

Foreign key actions

  • ON DELETE CASCADE — delete child rows when parent is deleted.
  • ON DELETE SET NULL — null out FK when parent is deleted.
  • NO ACTION (default) — block delete/update if children exist.

Key Points

  • Prefer constraints over triggers when the rule is simple (CHECK, FK, UNIQUE).
  • SELECT INTO does not copy constraints—add them afterward.
  • Constraints can be NOCHECK disabled for bulk loads (use carefully).

Interview Answer

Constraints enforce data integrity at the database layer—PK and UNIQUE for uniqueness, FK for relationships, CHECK and NOT NULL for business rules, DEFAULT for missing values. I define them in the schema so every application gets the same rules, and I use constraints before triggers when they are enough.

Database Relationships (1:1, 1:N, M:N)

Relationships describe how rows in one table link to rows in another. In relational databases they are implemented with primary keys, foreign keys, and sometimes a junction (bridge) table.

RelationshipDescriptionReal-world example
One-to-One (1:1)One record in Table A links to exactly one record in Table BEmployee ↔ EmployeeProfile (one person, one profile)
One-to-Many (1:N)One parent record has many child recordsCustomer → many Orders
Many-to-Many (M:N)Many records on both sides; resolved via a junction tableStudents ↔ Courses (via Enrollment)

One-to-One (1:1)

Each row on side A matches at most one row on side B, and vice versa.

When to use: split optional or sensitive columns into a separate table, or divide a wide table without duplicating the main entity.

Employees(EmployeeId PK, Name, ...)
EmployeeProfiles(EmployeeId PK/FK UNIQUE, Bio, PhotoUrl, ...)
-- EmployeeId is PK and FK → enforces 1:1

Implementation: share the same primary key, or put a UNIQUE constraint on the foreign key column so one parent maps to one child only.

One-to-Many (1:N)

The most common relationship. The “one” side holds the primary key; the “many” side stores a foreign key pointing to the parent.

Customers(CustomerId PK, Name)
Orders(OrderId PK, CustomerId FK → Customers, OrderDate)

-- One customer, many orders:
SELECT c.Name, o.OrderId, o.OrderDate
FROM Customers c
JOIN Orders o ON c.CustomerId = o.CustomerId;

Rule: FK goes on the many side (child table). Use ON DELETE CASCADE or SET NULL based on business rules.

Many-to-Many (M:N)

Neither table should hold a direct FK to the other—you cannot store multiple FK values cleanly in one column. Use a junction (associative) table with composite PK or unique pair of FKs.

Students(StudentId PK, Name)
Courses(CourseId PK, Title)
Enrollment(StudentId FK, CourseId FK, EnrolledOn,
           PRIMARY KEY (StudentId, CourseId))

-- Student takes many courses; course has many students

Query pattern: join through the junction table.

SELECT s.Name, c.Title
FROM Students s
JOIN Enrollment e ON s.StudentId = e.StudentId
JOIN Courses c ON e.CourseId = c.CourseId;

ISNULL vs COALESCE

Both replace NULL with a value. ISNULL is SQL Server–specific, takes exactly two arguments, and uses the first argument's data type. COALESCE is ANSI-standard, accepts multiple arguments, and returns the first non-NULL value.

  COALESCE(MiddleName, NickName, 'N/A') AS Display
FROM Employees;

Key Points

  • ISNULL can truncate if types differ; COALESCE follows precedence rules.
  • Prefer COALESCE for portability and multiple fallbacks.

Interview Answer

ISNULL replaces NULL with one fallback and is SQL Server–specific. COALESCE is standard, supports multiple fallbacks, and is my default unless I need ISNULL's two-arg simplicity in T-SQL.

Common Table Expressions (CTE)

A CTE is a temporary named result set defined with WITH, scoped to a single statement. It improves readability for recursive queries and multi-step transformations without creating permanent objects.

)

JOIN Departments d ON t.DeptId = d.DeptId;

  • Can reference multiple CTEs in one WITH clause.

Interview Answer

A CTE is a named subquery using WITH that makes complex SQL readable and supports recursion. It's scoped to one statement and doesn't persist like a temp table unless the optimizer materializes it.

SQL Injection

SQL injection occurs when untrusted input is concatenated into SQL, letting attackers alter queries—reading data, bypassing auth, or executing destructive commands.

Stored procedures help only when parameters are used—not dynamic SQL built with string concatenation inside the SP.

-- VULNERABLE:
"SELECT * FROM Users WHERE UserName = '" + input + "'"
-- input: ' OR '1'='1

-- SAFE: parameterized query
SqlCommand cmd = new("SELECT * FROM Users WHERE UserName = @u", conn);
cmd.Parameters.AddWithValue("@u", input);

Key Points

  • Always use parameterized queries or ORM parameter binding.
  • Never concatenate user input; validate and least-privilege DB accounts.
  • SPs help only if parameters are used—not dynamic SQL inside.

Interview Answer

SQL injection happens when user input becomes executable SQL. I prevent it with parameterized queries, avoid dynamic concatenation, apply least privilege, and use input validation as defense in depth.

SQL Triggers — Purpose

Triggers are special stored procedures that fire automatically on INSERT, UPDATE, or DELETE (and sometimes DDL). They enforce rules, audit changes, or maintain derived data—but add hidden complexity.

Purpose (why use them)

  • Audit trail — log who changed what and when (inserted/deleted tables).
  • Business rules — enforce cross-row constraints that CHECK constraints cannot express.
  • Derived data — maintain summary or cache tables when source rows change.
  • Replication / integration — queue outbound events on DML (use carefully).

inserted and deleted pseudo-tables hold new and old row versions for DML triggers.

CREATE TRIGGER trg_AuditEmployeeUpdate
ON Employees AFTER UPDATE
AS
BEGIN
  INSERT INTO EmployeeAudit(EmployeeId, OldSalary, NewSalary, ChangedAt)
  SELECT d.EmployeeId, d.Salary, i.Salary, GETDATE()
  FROM deleted d JOIN inserted i ON d.EmployeeId = i.EmployeeId;
END;

Key Points

  • AFTER vs INSTEAD OF triggers serve different use cases.
  • Triggers can cascade and hurt debugging—prefer constraints when possible.
  • inserted/deleted pseudo-tables hold old and new row versions.

Interview Answer

Triggers auto-run on data changes for auditing or enforcement. I use them sparingly because they're implicit side effects—prefer constraints and application logic unless cross-cutting audit is required.

ROW_NUMBER()

ROW_NUMBER() assigns a unique sequential integer to each row within a partition, ordered by specified columns. It's the go-to function for top-N per group and pagination.

Filter via subquery/CTE because window functions can't go in WHERE directly. Ties get different row numbers arbitrarily—use RANK for ties with gaps.

SELECT EmployeeId, Name, Salary,
  ROW_NUMBER() OVER (PARTITION BY DeptId ORDER BY Salary DESC) AS rn
FROM Employees;

-- 2nd highest salary per dept:
SELECT * FROM (
  SELECT *, ROW_NUMBER() OVER (PARTITION BY DeptId ORDER BY Salary DESC) rn
  FROM Employees
) x WHERE rn = 2;

Key Points

  • Ties get different row numbers—use RANK for ties with gaps.
  • PARTITION BY defines groups; ORDER BY defines sequence within group.
  • Filter via subquery/CTE—window functions can't go in WHERE directly.

Interview Answer

ROW_NUMBER() numbers rows within partitions—perfect for top-N per group and pagination. Unlike RANK, it never repeats numbers even when values tie.

Deadlocks

A deadlock occurs when two or more sessions hold locks each other needs, forming a cycle. SQL Server detects deadlocks, picks a victim, rolls back its transaction, and returns error 1205.

Access resources in consistent order across transactions and keep transactions short.

-- Session A                    -- Session B
BEGIN TRAN                      BEGIN TRAN
UPDATE Accounts SET ... Id=1    UPDATE Accounts SET ... Id=2
UPDATE Accounts SET ... Id=2    UPDATE Accounts SET ... Id=1
-- deadlock: one victim rolled back

Key Points

  • Access resources in consistent order across transactions.
  • Keep transactions short; avoid user interaction inside transactions.
  • Use appropriate isolation; retry victim transactions in app code.

Interview Answer

Deadlocks are circular lock waits—SQL Server kills one session. I prevent them by consistent lock ordering, short transactions, proper indexes to reduce lock time, and retry logic for 1205 errors.

NOLOCK Hint (READ UNCOMMITTED)

WITH (NOLOCK) or READ UNCOMMITTED allows reading uncommitted data—dirty reads, non-repeatable reads, and phantom rows are possible. It reduces blocking but sacrifices consistency.

Prefer READ COMMITTED SNAPSHOT for read concurrency without dirty reads on critical data.

SELECT * FROM Orders WITH (NOLOCK)
WHERE OrderDate >= '2024-01-01';

-- Equivalent session setting:
SET TRANSACTION ISOLATION LEVEL READ UNCOMMITTED;

Key Points

  • Never use NOLOCK on financial or authoritative reporting data.
  • Can read rows that roll back or see inconsistent page states.
  • Prefer READ COMMITTED SNAPSHOT for read concurrency without dirty reads.

Interview Answer

NOLOCK reads without shared locks, allowing dirty reads and inconsistencies. I avoid it for critical data; if I need read concurrency, I use RCSI or snapshot isolation instead.

SQL Transactions

A transaction groups one or more operations into an atomic unit following ACID: Atomicity, Consistency, Isolation, Durability. Either all changes commit or all roll back.

Use TRY/CATCH with XACT_ABORT ON in modern T-SQL; keep transactions short to reduce lock duration and deadlocks.

BEGIN TRANSACTION;
  UPDATE Accounts SET Balance = Balance - 100 WHERE Id = 1;
  UPDATE Accounts SET Balance = Balance + 100 WHERE Id = 2;
  IF @@ERROR <> 0 ROLLBACK TRANSACTION;
  ELSE COMMIT TRANSACTION;

Key Points

  • Keep transactions short to reduce lock duration and deadlocks.
  • Use TRY/CATCH with XACT_ABORT ON in modern T-SQL.
  • Nested transactions use @@TRANCOUNT; savepoints allow partial rollback.

Interview Answer

Transactions ensure ACID—either all SQL in the batch succeeds or none does. I wrap related DML in explicit transactions, handle errors with rollback, and keep them as short as possible.

MERGE Statement

MERGE performs INSERT, UPDATE, or DELETE in one statement based on a join between target and source. Useful for upserts and synchronizing staging to production tables.

Requires proper indexes on join keys; known concurrency issues exist under heavy contention—consider separate INSERT/UPDATE paths.

MERGE Products AS t
USING StagingProducts AS s ON t.ProductId = s.ProductId
WHEN MATCHED THEN UPDATE SET t.Price = s.Price
WHEN NOT MATCHED THEN INSERT (ProductId, Price)
  VALUES (s.ProductId, s.Price)
WHEN NOT MATCHED BY SOURCE THEN DELETE;

Key Points

  • Requires proper indexes on join keys for performance.
  • Known concurrency issues—consider separate INSERT/UPDATE in high contention.
  • OUTPUT clause can capture merged rows for auditing.

Interview Answer

MERGE upserts and syncs target tables from a source in one statement. I use it for ETL staging loads but watch for locking and known race conditions under heavy concurrency.

How Claims Work in JWT

A claim is a statement about the subject (user or client), stored as a name–value pair in the JWT payload (middle part). After Base64URL decode, the payload is JSON. The server (or identity provider) puts claims in when issuing the token; the API reads them after signature and lifetime validation.

JWT structure (three parts)

  1. Header — algorithm and type (alg, typ).
  2. Payload — claims (who, what roles, when it expires).
  3. Signature — proves the payload was not tampered with.

Example payload (claims):

{
  "sub": "user-42",
  "email": "user@example.com",
  "role": "Admin",
  "iss": "https://my-api.com",
  "aud": "https://my-api.com",
  "exp": 1717000000,
  "iat": 1716996400
}

2. Token service

public interface ITokenService
{
    string GenerateToken(User user);
}

public class TokenService : ITokenService
{
    private readonly IConfiguration _config;

    public TokenService(IConfiguration config) => _config = config;

    public string GenerateToken(User user)
    {
        var key = new SymmetricSecurityKey(
            Encoding.UTF8.GetBytes(_config["Jwt:Key"]!));
        var credentials = new SigningCredentials(key, SecurityAlgorithms.HmacSha256);

        var claims = new[]
        {
            new Claim(JwtRegisteredClaimNames.Sub, user.Id.ToString()),
            new Claim(JwtRegisteredClaimNames.Email, user.Email),
            new Claim(ClaimTypes.Role, user.Role)
        };

        var token = new JwtSecurityToken(
            issuer: _config["Jwt:Issuer"],
            audience: _config["Jwt:Audience"],
            claims: claims,
            expires: DateTime.UtcNow.AddMinutes(
                int.Parse(_config["Jwt:ExpireMinutes"]!)),
            signingCredentials: credentials);

        return new JwtSecurityTokenHandler().WriteToken(token);
    }
}

Async & Await in C#

async/await enables non-blocking asynchronous code. The compiler rewrites an async method into a state machine that can suspend at await and resume when the awaited Task completes — without holding a thread while waiting on I/O.

// I/O-bound — thread is released while waiting
public async Task<User> GetUserAsync(int id)
{
    var response = await _httpClient.GetAsync($"/users/{id}");
    response.EnsureSuccessStatusCode();
    return await response.Content.ReadFromJsonAsync<User>();
}

// Multiple awaits — sequential flow, still readable
public async Task<OrderSummary> BuildSummaryAsync(int orderId)
{
    var order = await _repo.GetOrderAsync(orderId);
    var customer = await _repo.GetCustomerAsync(order.CustomerId);
    return new OrderSummary(order, customer);
}

// Parallel I/O
var tasks = ids.Select(id => GetUserAsync(id));
var users = await Task.WhenAll(tasks);

How It Works

  • async on a method returns Task or Task<T> (or void for event handlers only).
  • At each await, if the operation is incomplete, the method returns control to the caller; the thread can serve other work.
  • When the awaited task completes, the state machine resumes — often on a thread-pool thread (ASP.NET Core has no sync context by default).
  • Exceptions thrown inside an async method are captured on the returned Task and rethrown when you await it.

async/await vs Task.Run

Use async/await for I/O-bound work (HTTP, DB, files). Use Task.Run only to offload CPU-bound synchronous code to the thread pool — wrapping I/O in Task.Run wastes threads.

Key Points

  • Prefer async Task over async void except for event handlers.
  • Avoid .Result and .Wait() on async code — can deadlock on UI or legacy ASP.NET.
  • ConfigureAwait(false) in library code avoids capturing synchronization context.
  • async all the way down: async controllers/services/repos compose cleanly.

Interview Answer

async/await lets you write sequential-looking code that does not block threads during I/O. The compiler builds a state machine around Tasks. I use it for HTTP, database, and file operations; I avoid blocking on Tasks and I do not wrap async I/O in Task.Run on server code.

.NET Garbage Collector

The GC reclaims managed heap memory for objects no longer reachable from GC roots (stack, static fields, CPU registers). It uses generational collection: Gen0 (short-lived), Gen1 (buffer), Gen2 (long-lived), plus LOH for large objects.

How It Works

  1. Mark — Starting from roots, the GC traces object references and marks every reachable object.
  2. Sweep / compact — Unmarked objects are reclaimed; on younger generations the heap may be compacted to reduce fragmentation.
  3. Promote survivors — Objects that survive a Gen0 collection move to Gen1; survivors of Gen1 move to Gen2. Long-lived objects are collected less often.
  4. Finalizers — Objects with destructors go to a finalizer queue; they survive one extra collection cycle (prefer IDisposable instead).

Collections are triggered when a generation budget is exceeded or under memory pressure. Full Gen2 collections are the most expensive.

// Gen0 collections are frequent and cheap
var list = new List<byte[]>();
for (int i = 0; i < 1000; i++)
    list.Add(new byte[100]); // mostly Gen0, ephemeral

// LOH allocations (>= 85 KB) collected less often
var big = new byte[100_000];

// Reduce GC pressure — pool/reuse
var buffer = ArrayPool<byte>.Shared.Rent(4096);
try { /* use buffer */ }
finally { ArrayPool<byte>.Shared.Return(buffer); }

Key Points

  • Generational hypothesis: most objects die young.
  • Full GC (Gen2) is expensive—avoid unnecessary allocations in hot paths.
  • IDisposable is for unmanaged resources; GC handles managed memory.
  • Server GC vs Workstation GC tuned for throughput vs interactive apps.

Interview Answer

The GC is a generational, tracing collector: it marks reachable objects from roots, frees unreachable ones, and promotes survivors across Gen0/Gen1/Gen2 to keep collections cheap for short-lived objects. I minimize allocations in hot paths, avoid LOH churn, and use IDisposable for unmanaged resources the GC does not know about.

throw vs throw ex

throw; rethrows the current exception preserving the original stack trace. throw ex; (or throw someCaughtEx) resets the stack trace to the rethrow site, hiding where the error actually occurred—bad for diagnostics.

try
{
    await _repo.SaveAsync(entity);
}
catch (SqlException ex)
{
    _logger.LogError(ex, "DB save failed");
    throw; // correct — original stack preserved
}

// Anti-pattern
catch (Exception ex)
{
    throw ex; // stack starts here — loses root frame info
}

// Wrapping when adding context
catch (Exception ex)
{
    throw new OrderProcessingException("Save failed", ex);
}

Key Points

  • Always use bare throw; inside catch to rethrow.
  • throw ex resets StackTrace—avoid in production code.
  • Wrap with inner exception when translating domain errors.
  • ExceptionDispatchInfo.Capture(ex).Throw() preserves stack outside catch.

Interview Answer

Use throw; to rethrow without losing stack trace. Use throw ex; only if you intentionally want a new stack (rare). When wrapping, pass the original as InnerException for full context.

await next(context) passes the request to the next middleware in the pipeline. Code before next runs on the way in; code after runs on the way out when the response travels back. Omitting next short-circuits the pipeline—useful for auth failures or cached responses.

Always await next so exceptions propagate correctly and the response is fully generated before post-processing.

    await next(context);
    // outbound — response headers/body available
}

Task.Run Explained

Task.Run queues a delegate on the .NET thread pool for CPU-bound work. The caller gets a Task immediately; pool threads execute the delegate concurrently. It is ideal when synchronous, compute-heavy code would block a sensitive thread (UI, ASP.NET request thread in older patterns).

// Offload CPU work
var result = await Task.Run(() => SimulateMonteCarlo(iterations: 1_000_000));

// Overload with CancellationToken
var cts = new CancellationTokenSource(TimeSpan.FromSeconds(30));
await Task.Run(() => ProcessBatch(items, cts.Token), cts.Token);

// Long-running alternative when you need a dedicated thread
await Task.Factory.StartNew(
    () => LongRunningListener(),
    TaskCreationOptions.LongRunning);

Key Points

  • Schedules work to ThreadPool—not for I/O-bound async APIs.
  • Returns hot Task; exceptions stored on Task, surfaced on await/Wait.
  • Prefer async I/O APIs over Task.Run for network/database calls.
  • LongRunning creates a non-pool thread when pool starvation is a risk.

Interview Answer

Task.Run moves CPU-bound synchronous work to a background thread-pool thread and returns a Task you can await. Use it for parallel computation, not as a substitute for truly asynchronous I/O.

Thread vs Task

A Thread is an OS-level execution unit—you create it, set priority, and manage its lifetime manually. A Task is a higher-level abstraction representing work that the thread pool may run; the runtime schedules Tasks onto available threads efficiently.

// Thread — explicit, heavier
var thread = new Thread(() => DoWork()) { IsBackground = true };
thread.Start();
thread.Join();

// Task — preferred for most scenarios
await Task.Run(() => DoWork());

// Task enables composition
var tasks = urls.Select(url => DownloadAsync(url));
await Task.WhenAll(tasks);

Key Points

  • Threads are expensive (~1 MB stack); pool reuse is cheaper.
  • Tasks support await, WhenAll, cancellation, and exception aggregation.
  • Creating many raw Threads can hurt scalability; Task uses pool.
  • Use dedicated Thread only for STA COM, long-blocking listeners, or special cases.

Interview Answer

Threads are low-level OS workers you manage directly. Tasks represent units of work scheduled by the thread pool with rich async composition. In modern .NET, prefer Task/async unless you have a specific reason to own a Thread.

Task.Wait and Blocking Pitfalls

Task.Wait(), Task.Result, and GetAwaiter().GetResult() synchronously block the calling thread until the Task completes. On contexts with a synchronization context (UI, legacy ASP.NET), blocking while waiting for code that needs that same context causes deadlocks.

// Dangerous on UI / ASP.NET (deadlock risk)
public Order GetOrderBlocking(int id)
{
    return _service.GetOrderAsync(id).Result; // blocks
}

// Preferred
public async Task<Order> GetOrderAsync(int id)
{
    return await _service.GetOrderAsync(id);
}

// Library code avoiding context capture
await _httpClient.GetAsync(url).ConfigureAwait(false);

Key Points

  • Never block on async code in ASP.NET Core request paths if avoidable.
  • AggregateException wraps Task exceptions on Wait/Result—harder to debug.
  • async all the way down is the scalable pattern.
  • ConfigureAwait(false) in libraries reduces deadlock on sync-over-async.

Interview Answer

Task.Wait blocks the current thread until completion. Avoid it in async-friendly apps—use await instead. Blocking on incomplete Tasks tied to the same synchronization context is a common deadlock source.

Preventing Memory Leaks in .NET

.NET has GC, but leaks still occur when rooted objects hold references to objects that should be collected—event handlers, static caches, undisposed unmanaged resources, and long-lived collections capturing short-lived contexts.

// Leak: subscriber never unsubscribes
publisher.Raised += OnRaised;

// Fix: unsubscribe or weak event pattern
publisher.Raised -= OnRaised;

// Always dispose unmanaged / IDisposable resources
await using var conn = new SqlConnection(cs);
await conn.OpenAsync();

// Avoid capturing large graphs in static caches without eviction
_cache.Set(key, value, TimeSpan.FromMinutes(5));

Key Points

  • Unsubscribe events or use WeakReference for long-lived publishers.
  • Implement IDisposable/IAsyncDisposable for files, sockets, handles.
  • Be cautious with static fields, singletons, and Timer callbacks.
  • Profile with dotMemory, PerfView, or VS Diagnostic Tools for retained paths.

Interview Answer

Prevent leaks by breaking unintended object graphs: unsubscribe events, dispose resources, limit static/cache retention, and avoid holding references to UI or request-scoped objects in singletons. Use profiling to find what keeps objects alive.

yield return and Iterators

yield return builds an iterator: the compiler generates a state machine implementing IEnumerable<T> or IAsyncEnumerable<T>. Elements are produced lazily on demand—memory-efficient for large or infinite sequences.

public IEnumerable<int> GetSquares(int max)
{
    for (int i = 0; i < max; i++)
        yield return i * i;
}

foreach (var sq in GetSquares(1_000_000)) { /* one at a time */ }

// Async streaming (.NET Core+)
async IAsyncEnumerable<Order> StreamOrdersAsync()
{
    await foreach (var batch in _repo.ReadBatchesAsync())
        foreach (var order in batch)
            yield return order;
}

  • Lazy evaluation—work runs when enumerator moves Next.

Alternatives to Task.WhenAll

Task.WhenAll waits for multiple Tasks concurrently. Alternatives depend on semantics: fail-fast vs collect-all-errors, throttling, sequential dependency, or parallel loops over CPU work.

// WhenAll — all parallel, one exception on await (others may still run)
var results = await Task.WhenAll(tasks);

// WhenAny — first completion (timeout/race pattern)
var finished = await Task.WhenAny(task, Task.Delay(5000));

// Parallel.ForEachAsync — bounded parallelism (.NET 6+)
await Parallel.ForEachAsync(items,
    new ParallelOptions { MaxDegreeOfParallelism = 4 },
    async (item, ct) => await ProcessAsync(item, ct));

// Manual throttling with SemaphoreSlim
using var gate = new SemaphoreSlim(4);
var throttled = items.Select(async i => {
    await gate.WaitAsync();
    try { return await WorkAsync(i); }
    finally { gate.Release(); }
});
await Task.WhenAll(throttled);

Key Points

  • WhenAny for timeouts, caching first response, or competitive calls.
  • Parallel.ForEach/ForEachAsync for CPU-bound batch with degree control.
  • SemaphoreSlim limits concurrent I/O when APIs have rate limits.
  • Task.WhenAll fails on first fault unless you observe all Task.Exception.

Interview Answer

Use WhenAll for unconstrained parallel awaits. Use WhenAny for first-wins scenarios, Parallel.ForEachAsync for bounded CPU parallelism, and SemaphoreSlim when you must cap concurrent operations. Choose based on error handling and resource limits.

Parallel Programming in .NET

Parallel programming splits work across cores. .NET offers Parallel (PLINQ, Parallel.For/ForEach), TPL Dataflow for pipelines, and async coordination via Tasks. Effective parallelism requires CPU-bound work and minimal shared mutable state.

// Parallel.For — partition work across cores
Parallel.For(0, items.Length, i => Process(items[i]));

// PLINQ
var primes = Enumerable.Range(2, 10000)
    .AsParallel()
    .WithDegreeOfParallelism(4)
    .Where(IsPrime)
    .ToList();

// Thread-safe aggregation
var bag = new ConcurrentBag<Result>();
Parallel.ForEach(source, item => bag.Add(Transform(item)));

Key Points

  • Parallelism helps CPU-bound work—not blocked I/O (use async there).
  • Race conditions need locks, Interlocked, or concurrent collections.
  • Over-parallelization adds scheduling overhead—tune MaxDegreeOfParallelism.
  • Amdahl's Law: speedup limited by serial portions of algorithm.

Interview Answer

.NET parallel APIs map work to multiple cores via the thread pool. Use Parallel/PLINQ for CPU-heavy batches with controlled concurrency and thread-safe aggregation. Combine with async for I/O, not as a replacement.

Multithreading Fundamentals

Multithreading runs multiple threads within one process sharing memory space. It improves throughput for parallel workloads but introduces complexity: race conditions, deadlocks, and visibility issues without proper synchronization.

private readonly object _lock = new();
private int _count;

void Increment()
{
    lock (_lock) { _count++; } // mutual exclusion
}

// Or lock-free
Interlocked.Increment(ref _count);

// Reader/writer scenario
private readonly ReaderWriterLockSlim _rw = new();
_rw.EnterReadLock();
try { /* read shared data */ }
finally { _rw.ExitReadLock(); }

Key Points

  • Shared mutable state requires synchronization (lock, Monitor, SemaphoreSlim).
  • Prefer higher abstractions (Task, ConcurrentDictionary) over raw locks when possible.
  • Deadlock: circular lock acquisition—consistent lock ordering prevents it.
  • volatile/Interlocked address visibility and atomic ops, not complex invariants.

Interview Answer

Multithreading executes concurrent paths in one process for parallelism. Success depends on identifying shared state, choosing correct synchronization, and avoiding deadlocks and races—often by immutability or concurrent collections.

Repository Pattern

Repository mediates between domain and data mapping layers, exposing collection-like access to aggregates while hiding persistence details (EF, Dapper, SQL). It improves testability and centralizes query logic.

  • Unit of Work often pairs with Repository for transaction boundaries.

Interview Answer

Encapsulation in C#

Encapsulation is an OOP principle that bundles data and behavior inside a class while hiding internal state from outside code. In C#, you achieve this with access modifiers (private, protected, internal) and controlled entry points such as properties and methods.

Instead of exposing fields directly, you validate and transform data through properties. This prevents invalid states, localizes change, and makes classes easier to test and maintain.

public class BankAccount

    {
        if (amount <= 0) throw new ArgumentException("Amount must be positive.");

}

Key Points

  • Hides implementation details and protects invariants.
  • Properties provide read/write control without breaking encapsulation.
  • Encapsulation improves maintainability and reduces coupling.

Interview Answer

Encapsulation means keeping an object's data private and exposing only what is necessary through a public API. In C#, I use private fields with public properties or methods so validation and business rules stay inside the class. This protects data integrity and makes future changes safer.

Generics in C#

Generics let you write type-safe, reusable code without boxing value types or casting on every use. A generic class or method is defined with a type parameter (for example, T) that is resolved at compile time.

Collections like List<T> and patterns like repositories use generics to enforce correctness while staying flexible. The compiler generates specialized code for value types and shares code for reference types.

public class Repository<T> where T : class
{
    private readonly List<T> _items = new();
    public void Add(T item) => _items.Add(item);
    public T? Find(Predicate<T> match) => _items.Find(match);
}

var users = new List<User>();
users.Add(new User { Id = 1 }); // compile-time type safety

Key Points

  • Compile-time type safety; fewer runtime casts.
  • Constraints (where T : ...) limit allowed type arguments.
  • Avoids boxing for value types in generic collections.

Interview Answer

Generics allow reusable, strongly typed APIs like List<int> or Repository<Order> without sacrificing performance or safety. The compiler checks types at compile time, so I get IntelliSense and fewer InvalidCastException issues at runtime.

Why DbContext Is Scoped

DbContext is not thread-safe and tracks entity changes for a unit of work. Registering it as scoped gives each HTTP request its own context instance, aligning with one logical transaction per request and preventing cross-request state leakage.

A singleton DbContext would be shared across concurrent requests, causing race conditions and stale tracked entities. Transient DbContext per injection would multiply connections and break change tracking coherence within a request.

builder.Services.AddDbContext<AppDbContext>(options =>
    options.UseSqlServer(connectionString)); // scoped by default

Key Points

  • DbContext tracks entities per unit of work.
  • Scoped = one context per request scope.
  • Do not share DbContext across threads.

Interview Answer

EF Core DbContext is scoped because it is not thread-safe and represents a single unit of work per request. One instance per HTTP request ensures consistent change tracking and avoids concurrency bugs that would occur with a singleton context shared by all users.

A virtual method provides a default implementation that derived classes can optionally replace. Constructor Chaining in C#

Constructor chaining lets one constructor call another in the same class (this) or a base class constructor (base). This avoids duplicating initialization logic and ensures objects are always created in a valid state.

The called constructor runs first. Use : this(...) to forward to another constructor in the same type, and : base(...) to invoke a parent constructor before your own body executes.

public class Employee
{

    public string Name { get; }

    public Employee(int id, string name)
    {
        Id = id;
        Name = name;
    }
}

public class Manager : Employee
{
    public Manager(int id, string name) : base(id, name) { }
}

Key Points

  • this(...) chains constructors within the same class.
  • base(...) calls a base class constructor.
  • Chaining must be the first statement in the constructor header.

Interview Answer

Constructor chaining reuses initialization through this or base calls so setup logic is not duplicated. The chained constructor always runs first, which helps enforce consistent object construction across overloads and inheritance.

Why async/await When Task Already Exists?

Task and Task<T> represent ongoing or completed asynchronous work. Raw Tasks force manual continuation chaining (.ContinueWith, callbacks), exception handling, and return-value plumbing. async/await is syntactic sugar that compiles to a state machine: readable sequential code, automatic exception propagation, and correct Task return types for callers.

// Without async/await — hard to read and error-prone
Task<Order> GetOrderOld(int id)
{
    return _repo.GetCustomerAsync(id)
        .ContinueWith(t =>
        {
            if (t.IsFaulted) throw t.Exception!;
            return _repo.GetOrderAsync(t.Result.OrderId);
        }).Unwrap();
}

// With async/await — same semantics, clearer flow
async Task<Order> GetOrderAsync(int id)
{
    var customer = await _repo.GetCustomerAsync(id);
    return await _repo.GetOrderAsync(customer.OrderId);
}

Key Points

  • Task = the abstraction; async/await = ergonomic way to compose Tasks.
  • Await unwraps exceptions; ContinueWith requires manual fault checking.
  • Compiler generates IAsyncStateMachine—no magic threads, just continuations.
  • Methods marked async always return Task/Task<T> (or ValueTask) to callers.

Interview Answer

We still use Task—async/await does not replace it. Tasks model async operations; async/await lets us write and maintain that logic like synchronous code while preserving non-blocking behavior and proper exception flow.

Run(), Use(), and Map() in ASP.NET Core

In ASP.NET Core, Run(), Use(), and Map() are middleware extension methods used to build the HTTP request pipeline.

ASP.NET Core Request Pipeline

Client â†’ Middleware 1 â†’ Middleware 2 â†’ Middleware 3 â†’ Response

Each middleware can handle the request, pass it to the next middleware, or stop the pipeline.

1. app.Run()

Run() is a terminal middleware. It handles the request, does not call the next middleware, and the pipeline stops there.

app.Run(async context =>
{
    await context.Response.WriteAsync("Hello World");
});

Important: Anything written after Run() will never execute for that branch.

app.Run(async context =>
{
    await context.Response.WriteAsync("First Run");
});

app.Use(async (context, next) =>
{
    await next(); // NEVER executes for requests handled above
});

Analogy: Road closed here â€” no request moves further.

2. app.Use()

Use() adds custom middleware and can pass the request to the next middleware. Code runs before and after await next().

app.Use(async (context, next) =>
{
    await context.Response.WriteAsync("Middleware 1 Start\n");
    await next();
    await context.Response.WriteAsync("Middleware 1 End\n");
});

app.Run(async context =>
{
    await context.Response.WriteAsync("Run Middleware\n");
});

Output:

Middleware 1 Start
Run Middleware
Middleware 1 End

Flow: Middleware 1 Start â†’ Run Middleware â†’ Middleware 1 End

Common uses: authentication, authorization, logging, exception handling, CORS, routing.

app.UseAuthentication();
app.UseAuthorization();

If next() is not called, the pipeline stops:

app.Use(async (context, next) =>
{
    await context.Response.WriteAsync("Stopped");
    // next() not called â€” further middleware won't run
});

3. app.Map()

Map() creates a branch in the pipeline based on URL path.

app.Map("/home", homeApp =>
{
    homeApp.Run(async context =>
    {
        await context.Response.WriteAsync("Home Page");
    });
});

app.Map("/about", aboutApp =>
{
    aboutApp.Run(async context =>
    {
        await context.Response.WriteAsync("About Page");
    });
});

public class ExceptionMiddleware
{
    private readonly RequestDelegate _next;
    private readonly ILogger<ExceptionMiddleware> _logger;

    public ExceptionMiddleware(RequestDelegate next, ILogger<ExceptionMiddleware> logger)
    {
        _next = next;
        _logger = logger;
    }

    public async Task Invoke(HttpContext context)
    {
        try
        {
            await _next(context);
        }
        catch (Exception ex)
        {
            _logger.LogError(ex, "Unhandled exception occurred");
            await HandleException(context, ex);
        }
    }

    private static async Task HandleException(HttpContext context, Exception ex)
    {
        context.Response.ContentType = "application/json";

        var (statusCode, message) = ex switch
        {
            KeyNotFoundException => (StatusCodes.Status404NotFound, ex.Message),
            UnauthorizedAccessException => (StatusCodes.Status401Unauthorized, ex.Message),
            ArgumentException => (StatusCodes.Status400BadRequest, ex.Message),
            NotImplementedException => (StatusCodes.Status501NotImplemented, ex.Message),
            _ => (StatusCodes.Status500InternalServerError, "Internal server error")
        };

        context.Response.StatusCode = statusCode;

        await context.Response.WriteAsJsonAsync(new
        {
            success = false,
            message,
            statusCode
        });
    }
}

Resiliency and Polly in ASP.NET Core

Resiliency means your app keeps working (or fails gracefully) when dependencies are slow, down, or flaky. For HTTP calls between services, you handle transient faults (timeouts, 503, network blips) without taking down the whole system.

Polly is a .NET resilience library: it defines policies (retry, circuit breaker, timeout, etc.) and runs your code through them. With IHttpClientFactory, policies attach to named or typed HttpClient registrations.

Transient vs permanent failures

Retry?Examples
Yes (with limits)408, 429, 502, 503, 504, socket timeout, connection reset
No400 validation, 401/403 auth, 404 not found, business rule errors

Only retry idempotent operations unless you have deduplication (safe: GET; risky: POST that creates orders).

Common Polly policies

PolicyPurpose
RetryRe-attempt failed calls (often with exponential backoff)
Circuit breakerStop calling a failing service; fail fast; probe recovery later
TimeoutCancel calls that run too long
BulkheadLimit concurrent calls so one dependency cannot exhaust threads
FallbackReturn cached/default response when dependency fails

Circuit breaker states

  • Closed — normal; calls pass through; failures are counted.
  • Open — too many failures; calls fail immediately (no load on sick service).
  • Half-open — after break duration, one trial call; success closes circuit, failure reopens.

HttpClient + Polly (classic integration)

NuGet: Microsoft.Extensions.Http.Polly (wraps Polly for HTTP).

builder.Services.AddHttpClient<IPaymentClient, PaymentClient>(client =>
{
    client.BaseAddress = new Uri(builder.Configuration["Services:PaymentApi"]!);
    client.Timeout = TimeSpan.FromSeconds(30);
})
.AddTransientHttpErrorPolicy(policy =>
    policy.WaitAndRetryAsync(
        3,
        retryAttempt => TimeSpan.FromSeconds(Math.Pow(2, retryAttempt)),
        onRetry: (outcome, delay, attempt, ctx) =>
        {
            // log attempt, status, exception
        }))
.AddTransientHttpErrorPolicy(policy =>
    policy.CircuitBreakerAsync(
        handledEventsAllowedBeforeBreaking: 5,
        durationOfBreak: TimeSpan.FromSeconds(30)));

AddTransientHttpErrorPolicy retries HTTP 5xx, 408, and HttpRequestException (not 4xx client errors).

Combining policies (order matters)

Typical outer-to-inner order for HTTP: Timeout → Circuit breaker → Retry → actual request. Timeouts should bound total wait including retries.

// Manual policy wrap (conceptual)
var pipeline = Policy.WrapAsync(retryPolicy, circuitBreakerPolicy, timeoutPolicy);
await pipeline.ExecuteAsync(() => httpClient.GetAsync("/orders"));

.NET 8+ built-in resilience (alternative)

    .AddStandardResilienceHandler();

Interviews still expect Polly concepts; know both names if asked about “modern .NET.”

Design tips

  • Set HttpClient.Timeout and Polly timeout so they align; avoid unbounded retries.
  • Log each retry with correlation id; monitor circuit-open events.
  • Use IHttpClientFactory — do not create new HttpClient() per request.
  • Pair resilience with health checks and alerts on dependency failure rates.

Interview One-Liner

Singleton Pattern

Singleton ensures a class has exactly one instance and provides global access. Common for shared resources like configuration, logging, or connection pools—though DI containers often manage lifetime instead.

Thread-safe lazy initialization (Lazy<T> in C#) is essential; avoid Singleton abuse for every shared object.

public sealed class Logger {
  private static readonly Lazy<Logger> _instance =
    new(() => new Logger());
  public static Logger Instance => _instance.Value;
  private Logger() { }
  public void Log(string msg) => Console.WriteLine(msg);
}

Key Points

  • Thread-safe lazy initialization (Lazy<T> in C#).
  • Hard to unit test due to global state—prefer DI singleton scope.
  • Avoid Singleton abuse; not every shared object needs the pattern.

Interview Answer

Singleton guarantees one instance with global access—useful for shared config or logging. In modern apps I often register a single instance in DI rather than hand-rolling static Instance properties.

Single Responsibility Principle (SRP)

Definition: A class should have only one reason to change — one job or responsibility.

If a class handles validation, database access, and email sending, any change to email logic forces you to retest database code. Split responsibilities into separate classes.

Bad example

public class InvoiceService
{
    public void CreateInvoice(Order order) { /* business */ }
    public void SaveToDatabase(Invoice inv) { /* SQL */ }
    public void EmailPdf(Invoice inv) { /* SMTP */ }
}

Good example

public class InvoiceService
{
    private readonly IInvoiceRepository _repo;
    private readonly IEmailSender _email;
    public InvoiceService(IInvoiceRepository repo, IEmailSender email) { ... }

    public async Task CreateAndNotifyAsync(Order order)
    {
        var inv = BuildInvoice(order);
        await _repo.SaveAsync(inv);
        await _email.SendInvoiceAsync(inv);
    }
}

InvoiceRepository owns persistence; EmailSender owns SMTP; InvoiceService orchestrates only invoice workflow.

Interview Answer

SRP means one class, one responsibility. I split reporting, persistence, and messaging so each class changes for only one business reason—easier tests and safer refactors.

Liskov Substitution Principle (LSP)

Definition: Subtypes must be substitutable for their base type without breaking program correctness. If code expects a Bird to fly, an Ostrich subclass must not throw unexpectedly.

Bad example

public class Rectangle
{
    public virtual int Width { get; set; }
    public virtual int Height { get; set; }
    public int Area() => Width * Height;
}

public class Square : Rectangle
{
    public override int Width
    {
        set { base.Width = base.Height = value; } // breaks Rectangle expectations
    }
}

Code that sets width and height independently fails when given a Square.

Good example

public interface IShape { int Area(); }
public class Rectangle : IShape { /* width, height */ }
public class Square : IShape { /* side */ }

Or use small interfaces (IFlyingBird, IBird) so substitutable types honor the same contract.

Interview Answer

LSP means any derived class should work wherever the base is used without surprising behavior. I avoid forcing subclasses to override methods they cannot support; I prefer composition or segregated interfaces instead of brittle inheritance.

Can We Inject a Scoped Service into a Singleton?

Not directly. A singleton lives for the entire application lifetime, but a scoped service (e.g. DbContext) exists only for one request. Holding a scoped instance inside a singleton causes:

  • Stale data — same DbContext reused across users/requests
  • Memory leaks — disposed context still referenced
  • Thread-safety issues — concurrent requests share one context

ASP.NET Core DI throws at startup if it detects captive dependency (scoped → singleton).

Wrong

public class CacheWarmupService  // Singleton
{
    public CacheWarmupService(AppDbContext db) { } // INVALID: scoped in singleton
}

Correct: resolve scoped inside a scope

public class CacheWarmupService : IHostedService
{
    private readonly IServiceScopeFactory _scopeFactory;

    public CacheWarmupService(IServiceScopeFactory scopeFactory)
        => _scopeFactory = scopeFactory;

    public async Task StartAsync(CancellationToken ct)
    {
        using var scope = _scopeFactory.CreateScope();
        var db = scope.ServiceProvider.GetRequiredService<AppDbContext>();
        await db.Products.CountAsync(ct);
    }
}

Use IServiceScopeFactory (or IServiceProvider.CreateScope()) to create a short-lived scope, resolve scoped services, then dispose the scope.

Interview Answer

No—you should not inject scoped into singleton directly. The singleton would capture one request’s scoped instance forever. Use IServiceScopeFactory to create a scope when you need scoped work from a singleton or background service.

async/await vs Task.Run

async/await is for non-blocking asynchronous I/O (HTTP, database, file streams). It frees the calling thread while work completes and resumes on a synchronization context when the await finishes. Task.Run offloads CPU-bound work to a thread-pool thread; it does not make I/O async—it wraps synchronous CPU work so the UI or request thread stays responsive.

// I/O-bound: async/await (no extra thread while waiting)
public async Task<string> GetUserAsync(int id)
{
    var response = await _httpClient.GetAsync($"/users/{id}");
    return await response.Content.ReadAsStringAsync();
}

// CPU-bound: Task.Run (uses thread pool)
public async Task<int> ComputeHashAsync(byte[] data)
{
    return await Task.Run(() => ExpensiveHash(data));
}

// Anti-pattern: Task.Run around I/O
await Task.Run(() => _httpClient.GetStringAsync(url)); // wastes a thread

Key Points

  • async/await = cooperative, I/O-bound; Task.Run = parallel CPU on pool threads.
  • Never wrap pure async I/O in Task.Run on ASP.NET Core—it reduces scalability.
  • async void only for event handlers; prefer async Task everywhere else.
  • ConfigureAwait(false) in library code avoids deadlocks on UI/legacy ASP.NET.

Interview Answer

Use async/await when waiting on I/O so threads are not blocked. Use Task.Run when you must run CPU-intensive synchronous code off the caller thread. They solve different problems; combining them means async/await waits for CPU work queued via Task.Run, not replacing it.

Covering Index in SQL Server

A covering index is a nonclustered index that contains all columns needed by a query — either as key columns or in the INCLUDE list. SQL Server can satisfy the query from the index alone without a key lookup back to the clustered index/heap (a “covering” plan).

Why it helps

  • Avoids expensive bookmark/key lookups for each matching row
  • Reduces I/O when the query needs only a few columns from a wide table
  • Often turns a nested loop + lookup into a pure index seek/scan
-- Query needs DeptId filter + Name, Salary in result
SELECT Name, Salary
FROM Employees
WHERE DeptId = 10;

-- Covering index: key for seek, INCLUDE for other columns
CREATE NONCLUSTERED INDEX IX_Emp_Dept_Covering
ON dbo.Employees (DeptId)
INCLUDE (Name, Salary);

Covering index vs clustered index

ClusteredCovering (nonclustered)
Count per tableOneMany
StoresFull row orderKey + included columns only
Best forPrimary access path / range on PKSpecific high-frequency queries

Trade-offs

  • Wider indexes use more storage and slow INSERT/UPDATE/DELETE slightly
  • Too many covering indexes on one table hurts write-heavy workloads
  • Design for real workloads (Query Store / plan cache), not every ad-hoc query

How to verify

In the execution plan, look for Index Seek on your index with no Key Lookup operator. SET STATISTICS IO ON should show lower logical reads on the index.

Interview Answer

A covering index includes all columns a query needs via the index key and INCLUDE columns, so SQL Server avoids key lookups. I add them for hot read queries after confirming the plan with actual execution plans and IO stats.

Index Design Strategy on a Wide Table (~30 Columns)

You cannot index every column on a large OLTP table — too much write overhead and storage. Index design is driven by real query patterns, not column count.

What I analyze first

  1. Workload evidence — Query Store, plan cache, top stored procedures, reports (not hypothetical queries).
  2. Execution plans — scans, key lookups, sorts, hash spills on the million-row table.
  3. Read vs write ratio — heavy OLTP limits how many nonclustered indexes you add.

Query patterns that drive index keys

PatternWhat to index
WHERE equality (e.g. CustomerId = @id)Leading key column; prefer high-selectivity filters
WHERE range (e.g. OrderDate BETWEEN)Usually after equality columns in a composite index
JOIN keysForeign-key columns used in joins to this table
ORDER BY / GROUP BYKey or INCLUDE columns to avoid expensive sorts

Selectivity and complexity

  • High selectivity — good leading keys (OrderId, Email).
  • Low selectivity (Status, IsActive) — combine with selective columns or use a filtered index.
  • Non-sargable predicates — functions on indexed columns block seeks; rewrite query.
  • OR / complex filters — may need UNION rewrite or multiple filtered indexes.

Composite index column order

  1. Equality predicates first.
  2. Then range predicates.
  3. Align left-prefix with how queries filter.
  4. INCLUDE for SELECT-only columns (covering index).
-- WHERE CustomerId = @c AND OrderDate >= @from
-- SELECT OrderId, TotalAmount, Status

CREATE NONCLUSTERED INDEX IX_Orders_Customer_Date
ON dbo.Orders (CustomerId, OrderDate)
INCLUDE (OrderId, TotalAmount, Status);

Interview Answer

I use Query Store and execution plans to index selective WHERE/JOIN keys and INCLUDE columns for hot result sets — never all 30 columns. I order keys as equality then range, use filtered indexes for skewed subsets, and validate with seeks and lower logical reads.

AS

    SELECT OrderId, CustomerId, Amount, OrderDate
    INTO #Staging
    FROM dbo.Orders
    WHERE OrderDate >= @FromDate;

    CREATE INDEX IX_Staging ON #Staging (CustomerId);

    UPDATE s SET s.Amount = s.Amount * dbo.fn_Adjustment(s.CustomerId)
    FROM #Staging s;

    SELECT CustomerId, SUM(Amount) AS Total
    FROM #Staging
    GROUP BY CustomerId;
END;

Interview Answer

Coding Query: Second Highest Salary Department-Wise

Tables:

  • Employee — EmployeeID, EmployeeName, Salary, DepartmentID
  • Department — DepartmentID, DepartmentName

Output: EmployeeName, Salary, DepartmentName for employees with the second highest salary in their department.

Clarify ties (say this in the interview)

  • Second highest salary value (distinct rank) → use DENSE_RANK() = 2 (multiple employees if they share that salary).
  • Exactly one employee per department (2nd row) → use ROW_NUMBER() = 2 (arbitrary among salary ties).

Recommended solution (DENSE_RANK)

WITH SalaryRanked AS (
    SELECT
        e.EmployeeName,
        e.Salary,
        e.DepartmentID,
        DENSE_RANK() OVER (
            PARTITION BY e.DepartmentID
            ORDER BY e.Salary DESC
        ) AS SalaryRank
    FROM Employee e
)
SELECT
    r.EmployeeName,
    r.Salary,
    d.DepartmentName
FROM SalaryRanked r
INNER JOIN Department d
    ON r.DepartmentID = d.DepartmentID
WHERE r.SalaryRank = 2
ORDER BY d.DepartmentName, r.Salary DESC;

Alternative: ROW_NUMBER (one row per department)

WITH Ranked AS (
    SELECT
        e.EmployeeName,
        e.Salary,
        e.DepartmentID,
        ROW_NUMBER() OVER (
            PARTITION BY e.DepartmentID
            ORDER BY e.Salary DESC, e.EmployeeID
        ) AS rn
    FROM Employee e
)
SELECT r.EmployeeName, r.Salary, d.DepartmentName
FROM Ranked r
INNER JOIN Department d ON r.DepartmentID = d.DepartmentID
WHERE r.rn = 2;

Alternative: subquery (no window functions)

SELECT e.EmployeeName, e.Salary, d.DepartmentName
FROM Employee e
INNER JOIN Department d ON e.DepartmentID = d.DepartmentID
WHERE e.Salary = (
    SELECT MAX(e2.Salary)
    FROM Employee e2
    WHERE e2.DepartmentID = e.DepartmentID
      AND e2.Salary < (
          SELECT MAX(e3.Salary)
          FROM Employee e3
          WHERE e3.DepartmentID = e.DepartmentID
      )
);

Sample data check

-- Dept IT: salaries 120k, 120k, 90k → 2nd highest = 90k (DENSE_RANK = 2)
-- Dept HR: salaries 80k only → no row returned for rank 2

Key Points

  • PARTITION BY DepartmentID resets ranking per department.
  • Join Department last to get DepartmentName.
  • Filter window result in outer query or CTE (not in same-level WHERE).

Interview Answer

I rank salaries per department with DENSE_RANK() OVER (PARTITION BY DepartmentID ORDER BY Salary DESC), keep rank = 2, and join Department for the name. I confirm whether ties at the second salary should return multiple employees or a single row, then pick DENSE_RANK vs ROW_NUMBER.

Remove Duplicate Records Using CTE and PARTITION BY

Table: [User] with Email, UserID, UserName — no primary key.

Define what “duplicate” means (usually same Email, or same Email + UserName). Keep one row per duplicate group; delete the rest.

Step 1: Preview duplicates (CTE + ROW_NUMBER)

WITH UserCTE AS (
    SELECT
        Email,
        UserID,
        UserName,
        ROW_NUMBER() OVER (
            PARTITION BY Email          -- duplicate key: Email only
            ORDER BY UserID             -- which row to keep (lowest UserID)
        ) AS rn
    FROM dbo.[User]
)
SELECT Email, UserID, UserName, rn
FROM UserCTE
WHERE rn > 1;   -- rows that would be deleted

Step 2: Delete duplicates (required: CTE + PARTITION BY)

WITH UserCTE AS (
    SELECT
        Email,
        UserID,
        UserName,
        ROW_NUMBER() OVER (
            PARTITION BY Email, UserName   -- adjust partition to your duplicate rule
            ORDER BY UserID
        ) AS rn
    FROM dbo.[User]
)
DELETE FROM UserCTE
WHERE rn > 1;

Partition column choice

Duplicate rulePARTITION BY
Same email is duplicateEmail
Same email and usernameEmail, UserName
Entire row identicalEmail, UserName, UserID (only deletes exact copies if UserID differs)

ORDER BY in ROW_NUMBER (which row to keep)

  • ORDER BY UserID — keep smallest UserID.
  • ORDER BY UserName — keep arbitrary deterministic row.
  • Without a tie-breaker, which duplicate survives may be undefined.

If every column is identical (true duplicate rows)

With no PK and all columns equal, SQL Server cannot distinguish two physical rows. Options: add a surrogate key, use %%physloc%% in advanced cases, or delete via staging table with SELECT DISTINCT into a new table and swap.

-- Safer rebuild pattern (no PK, many exact duplicates)
SELECT DISTINCT Email, UserID, UserName
INTO dbo.User_Clean
FROM dbo.[User];

-- truncate/rename swap in controlled migration

Key Points

  • ROW_NUMBER() OVER (PARTITION BY ... ORDER BY ...) numbers duplicates; rn = 1 is kept.
  • SQL Server allows DELETE from a CTE built on a single base table with window function.
  • Always preview with SELECT before DELETE; backup or use a transaction.

Interview Answer

I use a CTE with ROW_NUMBER() OVER (PARTITION BY Email ORDER BY UserID), delete where rn > 1, and confirm the partition matches the business duplicate rule. I preview rows first and mention that identical rows with no distinguishing column need a different strategy.

What Is the N+1 Query Problem in EF Core?

The N+1 problem means you execute 1 query to load N parent rows, then N additional queries (one per row) to load related data — total N+1 round trips to the database.

Classic example (lazy loading or missing Include)

// 1 query - get 100 orders
var orders = await _context.Orders.ToListAsync();

// 100 queries - one per order when Customer is accessed
foreach (var order in orders)
{
    Console.WriteLine(order.Customer.Name);  // lazy load or manual load in loop
}

Total: 101 queries instead of 1–2.

Does N+1 happen with eager loading or lazy loading?

Loading styleN+1 risk?
Lazy loadingHigh — each navigation access in a loop can fire another query
No Include (default)High if you access navigations in loops
Eager loading (Include)Low — related data loaded with main query (JOIN or split query)
Explicit loading in loopHigh — same as N+1 if you Load() inside foreach
Projection to DTOLow — single SELECT with needed columns

Fix: eager load or project

// Eager - usually 1-2 queries
var orders = await _context.Orders
    .Include(o => o.Customer)
    .ToListAsync();

// Or projection - one query, no tracking overhead
var dtos = await _context.Orders
    .Select(o => new { o.Id, CustomerName = o.Customer.Name })
    .ToListAsync();

  • Use MiniProfiler or Application Insights dependency tracking
  • Watch for many similar SELECT statements per request

LINQ: Nth Highest Salary (e.g. Third Highest)

Given a list of employees, find the employee(s) at the 3rd distinct salary rank.

Sample data

var employees = new List<Employee>
{
    new() { Id = 1, Name = "A", Salary = 90000 },
    new() { Id = 2, Name = "B", Salary = 120000 },
    new() { Id = 3, Name = "C", Salary = 120000 },
    new() { Id = 4, Name = "D", Salary = 80000 },
    new() { Id = 5, Name = "E", Salary = 100000 }
};

Approach 1: Distinct salaries, order, skip, take (in-memory)

// Third highest DISTINCT salary value
int thirdHighestSalary = employees
    .Select(e => e.Salary)
    .Distinct()
    .OrderByDescending(s => s)
    .Skip(2)   // skip 1st and 2nd highest distinct salaries
    .First();  // 3rd distinct salary

// All employees with that salary
var thirdHighestEarners = employees
    .Where(e => e.Salary == thirdHighestSalary)
    .ToList();

Approach 2: One query for third highest earner (if unique rank)

var third = employees
    .OrderByDescending(e => e.Salary)
    .Skip(2)
    .Take(1)
    .FirstOrDefault();

Warning: Skip(2).Take(1).FirstOrDefault() picks the third row after sort, not necessarily the third distinct salary when ties exist (see below).

EF Core (database-side distinct ranks)

var thirdSalary = await _context.Employees
    .Select(e => e.Salary)
    .Distinct()
    .OrderByDescending(s => s)
    .Skip(2)
    .FirstOrDefaultAsync();

var employeesAtRank = await _context.Employees
    .Where(e => e.Salary == thirdSalary)
    .ToListAsync();

Same salary ties: why Skip/Take vs FirstOrDefault fails

If two employees share the top salary, sorting by salary descending gives:

120000 - B
120000 - C
100000 - E
90000  - A
80000  - D

Skip(2).Take(1).FirstOrDefault() returns E (100000) — the third row, not the third distinct salary rank (which would be 100000 only if ranks were 120k, 100k, 90k... but 120k occupied ranks 1 and 2).

FirstOrDefault() after filtering to one salary without Distinct() on salary ranks can return wrong person or arbitrary tie-breaker among equal salaries.

Correct pattern for Nth highest with ties

  1. Get distinct salaries ordered descending
  2. Skip(N-1) to get the Nth distinct salary value
  3. Filter all employees matching that salary if you need every tied employee
int n = 3;
int? nthDistinctSalary = employees
    .Select(e => e.Salary)
    .Distinct()
    .OrderByDescending(s => s)
    .Skip(n - 1)
    .FirstOrDefault();  // 0 if fewer than n distinct salaries

var result = nthDistinctSalary == null
    ? new List<Employee>()
    : employees.Where(e => e.Salary == nthDistinctSalary).ToList();

Interview Answer

For third highest salary I distinct and order salaries, Skip(2), then take that value and filter employees. Skip/Take on rows without Distinct fails when salaries tie because row position differs from salary rank. FirstOrDefault alone does not handle ties or distinct ranks—use Distinct on salary first.

Refresh Expired JWT with HTTP Interceptor (401)

When the API returns 401 Unauthorized during active use, intercept the error, call the refresh endpoint once, store the new access token, then retry the original request seamlessly.

RxJS operators used

  • catchError — detect 401 and branch to refresh logic
  • switchMap — chain refresh call, then retry original request with new token
  • throwError — propagate non-401 errors or failed refresh
  • filter / take(1) — wait until refresh completes (queue pattern)

Pattern: single in-flight refresh (avoid stampede)

@Injectable({ providedIn: 'root' })
export class AuthInterceptor implements HttpInterceptor {
  private refreshInFlight$: Observable<string> | null = null;

  constructor(
    private http: HttpBackend, // bypass interceptors for refresh call
    private tokens: TokenService,
    private router: Router
  ) {}

  intercept(req: HttpRequest<unknown>, next: HttpHandler): Observable<HttpEvent<unknown>> {
    const withToken = this.addToken(req);
    return next.handle(withToken).pipe(
      catchError((err: HttpErrorResponse) => {
        if (err.status !== 401 || req.url.includes('/auth/refresh')) {
          return throwError(() => err);
        }
        return this.refreshToken().pipe(
          switchMap((newAccess) => {
            this.tokens.setAccessToken(newAccess);
            return next.handle(this.addToken(req));
          }),
          catchError((refreshErr) => {
            this.tokens.clear();
            this.router.navigate(['/login']);
            return throwError(() => refreshErr);
          })
        );
      })
    );
  }

  private refreshToken(): Observable<string> {
    if (!this.refreshInFlight$) {
      this.refreshInFlight$ = this.http
        .post<{ accessToken: string }>('/api/auth/refresh', {})
        .pipe(
          map((r) => r.accessToken),
          finalize(() => (this.refreshInFlight$ = null)),
          shareReplay(1)
        );
    }
    return this.refreshInFlight$;
  }

  private addToken(req: HttpRequest<unknown>) {
    const token = this.tokens.getAccessToken();
    return token
      ? req.clone({ setHeaders: { Authorization: `Bearer ${token}` } })
      : req;
  }
}

Flow on 401 while user is active

  1. Request fails with 401.
  2. catchError triggers refresh (only one refresh if many requests fail via shared refreshInFlight$).
  3. switchMap retries original HTTP call with updated Authorization header.
  4. User sees no error if refresh succeeds; redirect to login if refresh fails.

Interview Answer

I handle 401 in an interceptor with catchError, refresh the token once using a shared in-flight Observable, then switchMap to retry the failed request. I use HttpBackend for the refresh call to avoid infinite loops and log out if refresh returns 401.

Stack vs Heap in C#

The stack holds value types and method call frames (local variables, return addresses) in LIFO order — fast allocation, automatic cleanup when a method returns. The heap holds objects referenced by reference types; memory is managed by the Garbage Collector.

StoresValue types, references (pointers), call framesObject instances (classes, arrays, boxed values)
AllocationVery fast (pointer bump)Slower; tracked by GC
LifetimeMethod scopeUntil no longer reachable
ThreadEach thread has its own stackShared managed heap

{

Key Points

  • Value types live on the stack when local; reference types live on the heap.
  • Large structs can live on the heap when boxed or embedded in heap objects.
  • Stack overflow = too deep recursion; heap pressure = too many allocations.

Interview Answer

The stack stores value types and call frames with automatic scope-based cleanup. The heap stores reference-type objects managed by the GC. Understanding both helps explain performance, boxing, and why minimizing heap allocations matters in hot paths.

Partial Class — What & Use

A partial class splits one class definition across multiple source files. The compiler merges all parts into a single type at compile time. All parts must use the partial keyword and belong to the same namespace and assembly.

// User.cs
public partial class User
{
    public int Id { get; set; }
    public string Name { get; set; }
}

// User.Validation.cs
public partial class User
{
    public bool IsValid() => !string.IsNullOrWhiteSpace(Name);
}

Common uses

  • Designer-generated code — WinForms/WPF Form1.Designer.cs separate from your logic.
  • Large classes — split by feature (validation, mapping, API) for readability.
  • Source generators — tooling emits another partial file.

Key Points

  • One class, multiple files — merged at compile time.
  • All parts must be partial with the same class name.
  • Cannot split a single method body across files.

Interview Answer

Partial classes let me split one class across files so generated UI code stays separate from business logic, or large types stay organized. The compiler combines all partial declarations into one class.

Can Partial Class Exist in Different Projects?

No — not across different assemblies/projects. All parts of a partial class must compile into the same assembly (same project, or files explicitly included in one project).

Partial types cannot span Project A and Project B because each project produces a separate DLL; the compiler merges partials only within one compilation unit.

Workarounds

  • Put all partial files in the same .csproj (can be different folders).
  • Use linked files in MSBuild to include a .cs file from another folder into one project — still one assembly.
  • Across projects use inheritance (class Derived : Base) or composition, not partial.
// ❌ User.cs in ProjectA + User.extra.cs in ProjectB — NOT valid partial

// ✅ User.cs + User.validation.cs both in same ProjectA

Interview Answer

Partial classes must live in the same project/assembly. Different projects produce different assemblies, so you cannot split one partial class across them — use inheritance or shared project references instead.

Hashtable vs Dictionary / HashSet vs Dictionary

Hashtable is legacy, non-generic, thread-safe for single writes; stores object keys/values with boxing. Dictionary<TKey,TValue> is the modern generic key-value map. HashSet<T> stores unique keys only — no values — optimized for membership and set operations.

HashtableKey → value (non-generic)Legacy code only — prefer Dictionary
Dictionary<K,V>Key → value (generic)Lookup by key, counts, caches

JWT — How It Works, Expiry & Content

A JSON Web Token (JWT) is a compact, signed string with three Base64URL-encoded parts: header.payload.signature. The API trusts the payload only if the signature matches and claims like exp are valid.

How JWT works (flow)

  1. Client sends credentials to POST /api/auth/login.
  2. Server validates user, builds claims, signs token with secret/private key, returns JWT.
  3. Client stores token and sends Authorization: Bearer <token> on each API call.
  4. JwtBearer middleware validates signature, issuer, audience, and expiry, then sets HttpContext.User.
  5. [Authorize] / policies check roles or claims before the action runs.

Token content (three parts)

// Header (algorithm + type)
{ "alg": "HS256", "typ": "JWT" }

// Payload — claims (NOT encrypted; only signed)
{
  "sub": "user-42",
  "email": "user@example.com",
  "role": "Admin",
  "iss": "https://my-api.com",
  "aud": "https://my-api.com",
  "exp": 1717000000,
  "iat": 1716996400
}

// Signature = HMAC(header + "." + payload, secret)

Expiry

  • exp (expiration) — Unix timestamp; token rejected after this time.
  • nbf (not before) — optional; token invalid before this time.
  • ASP.NET Core checks expiry when ValidateLifetime = true in TokenValidationParameters.
  • Short-lived access tokens (15–60 min) + refresh tokens is a common production pattern.
options.TokenValidationParameters = new TokenValidationParameters
{
    ValidateIssuer = true,
    ValidateAudience = true,
    ValidateLifetime = true,
    ClockSkew = TimeSpan.FromMinutes(1),
    ValidIssuer = config["Jwt:Issuer"],
    ValidAudience = config["Jwt:Audience"],
    IssuerSigningKey = new SymmetricSecurityKey(keyBytes)
};

Key Points

  • Payload is readable by anyone — do not put passwords or secrets in JWT.
  • Signature proves integrity; without it, claims can be tampered with.
  • Stateless — server does not store session; revocation needs blocklists or short expiry.

Interview Answer

JWT is a signed token with claims in the payload. The client sends it as a Bearer token; middleware validates signature, issuer, audience, and expiry before authorization runs. I keep access tokens short-lived, put identity and roles in claims, and never store sensitive data in the payload because it is only signed, not encrypted.

Can We Use [HttpPost] on a GET Action?

Technically yes — you can decorate any action with [HttpPost], but it will only respond to POST requests, not GET. The attribute defines which HTTP verb routes to that action; it does not change how the method works internally.

// This action is ONLY reachable via POST — not GET
[HttpPost("users/search")]
public IActionResult SearchUsers([FromBody] SearchCriteria criteria)
{
    return Ok(_repo.Search(criteria));
}

// GET /users/search → 405 Method Not Allowed (no matching GET action)
// POST /users/search → runs SearchUsers

Common confusion

  • Wrong pattern: naming an action GetUsers but marking it [HttpPost] — confusing for maintainers even if it compiles.
  • Correct pattern: GET for reads (no body), POST for creates or complex queries with large filters in body.
  • Some teams use POST for search when filter JSON is too large for query string — still not a GET action.

What happens if verb and attribute mismatch?

If the client sends GET but only a POST action exists, routing may match the route template but return 405 Method Not Allowed. If no route matches at all, returns 404.

Interview Answer

You can put [HttpPost] on any action, but then only POST requests hit it — a GET request will not execute that action. I align HTTP verbs with REST semantics: GET for safe reads, POST for creates or non-idempotent operations, rather than mixing verb names and attributes inconsistently.

What is a Stored Procedure (SP)?

A stored procedure is a precompiled batch of T-SQL statements saved in the database and executed by name. It can accept parameters, perform DML, contain business logic, transactions, and return result sets or status codes.

CREATE PROCEDURE dbo.GetEmployeesByDept
    @DeptId INT
AS
BEGIN
    SET NOCOUNT ON;

    SELECT EmployeeId, Name, Salary
    FROM Employees
    WHERE DeptId = @DeptId
    ORDER BY Name;
END;

-- Execute
EXEC dbo.GetEmployeesByDept @DeptId = 3;

Why use stored procedures?

  • Encapsulation — business rules live in one place close to data.
  • Security — grant EXEC without exposing base tables.
  • Performance — execution plan reuse; less network round trips.
  • Maintenance — change logic once without redeploying every client app.

A stored procedure is a named, reusable T-SQL program stored in the database. I use SPs to encapsulate data access and business rules, improve security via EXEC permissions, and reduce round trips. Parameters are passed at runtime with EXEC or from ADO.NET/EF raw SQL.

WHERE vs HAVING in SQL

Both filter rows, but at different stages of query execution. WHERE filters rows before grouping; HAVING filters groups after GROUP BY.

WHEREHAVING
FiltersIndividual rowsGrouped aggregates
Used withSELECT, UPDATE, DELETESELECT with GROUP BY
Aggregate functions?Cannot filter on SUM/COUNT directly*Can filter on SUM/COUNT/AVG
Order in queryBefore GROUP BYAfter GROUP BY

*Use a subquery or HAVING if you need to filter on an aggregate.

-- WHERE: filter rows before grouping
SELECT DeptId, COUNT(*) AS EmpCount
FROM Employees
WHERE Salary > 50000          -- row filter
GROUP BY DeptId;

-- HAVING: filter groups after aggregation
SELECT DeptId, COUNT(*) AS EmpCount
FROM Employees
GROUP BY DeptId
HAVING COUNT(*) > 5;          -- group filter

-- Both together
SELECT DeptId, AVG(Salary) AS AvgSal
FROM Employees
WHERE IsActive = 1            -- rows first
GROUP BY DeptId
HAVING AVG(Salary) > 60000;   -- groups second

Key Points

  • WHERE cannot reference aggregate aliases from SELECT — HAVING can use aggregates.
  • Filter individual rows with WHERE; filter summary results with HAVING.
  • Using HAVING where WHERE suffices is slower — filter early when possible.

Interview Answer

WHERE filters rows before grouping; HAVING filters after GROUP BY on aggregated results. I use WHERE for column conditions on raw rows and HAVING when the condition involves COUNT, SUM, or AVG of a group.

SQL Functions — Can They Have Multiple Return Types?

No — a single SQL Server function has one declared return type (scalar type or one table structure). You cannot return sometimes an int and sometimes a varchar from the same function.

RETURNS DECIMAL(10,2)

    RETURN @Sal * 0.10;

RETURNS TABLE

  • Use optional columns with NULLs in one consistent table shape.

A function has one return type — scalar or a fixed table definition. It cannot dynamically switch return types. For varying outputs I use separate functions, stored procedures, or return JSON from a scalar function when flexibility is required.

Query: If Commission Is NULL, Return 0

Use ISNULL, COALESCE, or NULLIF patterns to replace NULL with a default in SELECT expressions.

FROM Employees;

Get 5th Highest Salary

Rank salaries descending and filter where rank equals 5. Clarify whether ties count as separate ranks (ROW_NUMBER) or shared ranks (DENSE_RANK).

Method 1 — DENSE_RANK (5th distinct salary)

SELECT Salary
FROM (
    SELECT Salary,
           DENSE_RANK() OVER (ORDER BY Salary DESC) AS dr
    FROM Employees
) t
WHERE dr = 5;

Method 2 — ROW_NUMBER (5th row regardless of ties)

SELECT Salary
FROM (
    SELECT Salary,
           ROW_NUMBER() OVER (ORDER BY Salary DESC) AS rn
    FROM Employees
) t
WHERE rn = 5;

Method 3 — OFFSET (SQL Server 2012+)

SELECT DISTINCT Salary
FROM Employees
ORDER BY Salary DESC
OFFSET 4 ROWS FETCH NEXT 1 ROW ONLY;
-- skips 4 rows, returns 5th distinct value

Key Points

  • OFFSET 4 = skip first four — returns the 5th highest distinct salary.
  • DENSE_RANK skips no numbers when salaries tie; ROW_NUMBER assigns unique ranks.
  • Index on Salary DESC helps on large tables.

Interview Answer

For 5th highest salary I use DENSE_RANK or ROW_NUMBER over ORDER BY Salary DESC in a subquery and filter rank = 5, or OFFSET 4 ROWS FETCH NEXT 1 ROW ONLY on distinct salaries. I confirm whether ties should share the same rank before picking the function.

Department with 0 Employees

Find departments that exist in a master table but have no matching employees — classic LEFT JOIN with NULL check or NOT EXISTS.

-- LEFT JOIN — departments with no employees
SELECT d.DeptId, d.DeptName
FROM Departments d
LEFT JOIN Employees e ON e.DeptId = d.DeptId
WHERE e.EmployeeId IS NULL;

-- NOT EXISTS — often efficient with index on Employees.DeptId
SELECT d.DeptId, d.DeptName
FROM Departments d
WHERE NOT EXISTS (
    SELECT 1 FROM Employees e
    WHERE e.DeptId = d.DeptId
);

-- EXCEPT (if you only have employee dept ids)
SELECT DeptId FROM Departments
EXCEPT
SELECT DISTINCT DeptId FROM Employees WHERE DeptId IS NOT NULL;

Opposite — departments WITH employees

SELECT DISTINCT d.DeptId, d.DeptName
FROM Departments d
INNER JOIN Employees e ON e.DeptId = d.DeptId;

Key Points

  • LEFT JOIN + WHERE right.key IS NULL is the standard anti-join pattern.
  • NOT EXISTS often performs well and reads clearly for "no matching rows."
  • Index on Employees(DeptId) speeds the lookup.

Interview Answer

I LEFT JOIN Departments to Employees and filter where EmployeeId IS NULL, or use NOT EXISTS on Employees for that DeptId. Both return departments with zero employees; I pick based on readability and the execution plan.

How to Identify a Missing Index in SQL Server

Start with a slow query's execution plan, then confirm with DMVs and missing-index suggestions — but always test before creating indexes blindly.

1. Execution plan (SSMS)

  • Enable Actual Execution Plan (Ctrl+M).
  • Look for Table Scan / Clustered Index Scan on large tables.
  • Green Missing Index suggestion appears with impact % and CREATE INDEX script.

2. sys.dm_db_missing_index_* DMVs

SELECT
    migs.avg_user_impact,
    migs.user_seeks + migs.user_scans AS total_usage,
    mid.statement AS table_name,
    mid.equality_columns,
    mid.inequality_columns,
    mid.included_columns
FROM sys.dm_db_missing_index_groups mig
JOIN sys.dm_db_missing_index_group_stats migs
    ON mig.index_group_handle = migs.group_handle
JOIN sys.dm_db_missing_index_details mid
    ON mig.index_handle = mid.index_handle
ORDER BY migs.avg_user_impact * (migs.user_seeks + migs.user_scans) DESC;

3. Other signals

  • High logical reads in STATISTICS IO.
  • Key lookup + scan combinations on wide tables.
  • Query Store regressed plans after data growth.

Caution

  • Missing-index DMVs suggest — they do not account for write overhead or overlapping indexes.
  • Validate with plan before/after; drop unused indexes periodically.

Interview Answer

I capture the actual execution plan and look for scans and missing-index warnings. I also query dm_db_missing_index DMVs for high-impact suggestions. Before creating an index I check write load, column selectivity, and whether a covering index is needed — then measure again.

AsNoTracking in Entity Framework Core

By default EF Core tracks entities loaded from the database in the change tracker. AsNoTracking() tells EF to load entities as read-only snapshots — faster and lower memory, with no SaveChanges updates for those entities.

// Read-only list — no change tracking
var products = await _context.Products
    .AsNoTracking()
    .Where(p => p.IsActive)
    .ToListAsync();

// Default — tracked (for updates)
var product = await _context.Products.FindAsync(id);
product.Price = 99.99m;
await _context.SaveChangesAsync();  // UPDATE sent

// Global default for read-heavy APIs
options.UseQueryTrackingBehavior(QueryTrackingBehavior.NoTracking);

When to use AsNoTracking

  • GET/list/report queries that only return DTOs.
  • Large read-only result sets — less memory and CPU.
  • Projections with Select to anonymous types or DTOs (often no tracking anyway).

When NOT to use

  • When you load an entity, modify it, and call SaveChanges.
  • When you need navigation fix-up and later updates on the same context instance.

Azure Functions — Data Extraction from Request

In HTTP-triggered Azure Functions you read data from the incoming request via HttpRequestData (isolated worker) or HttpRequest (in-process). Data can come from the body, query string, route, or headers.

Isolated worker model (.NET 8 — recommended)

[Function("CreateOrder")]
public async Task<HttpResponseData> Run(
    [HttpTrigger(AuthorizationLevel.Function, "post", Route = "orders/{id}")]
    HttpRequestData req,
    int id,
    FunctionContext context)
{
    // Route parameter — bound automatically: id

    // Query string — ?status=pending
    var query = System.Web.HttpUtility.ParseQueryString(req.Url.Query);
    var status = query["status"];

    // Headers
    if (req.Headers.TryGetValues("X-Correlation-Id", out var corrIds))
        var correlationId = corrIds.FirstOrDefault();

    // JSON body
    var order = await req.ReadFromJsonAsync<CreateOrderDto>();

    var response = req.CreateResponse(HttpStatusCode.OK);
    await response.WriteAsJsonAsync(new { id, status, order });
    return response;
}

Open/Closed Principle — Violation Example

Open/Closed Principle (OCP): Software entities should be open for extension but closed for modification. Adding behavior should not require editing existing, tested code.

Violation — switch grows with every new type

public class InvoiceExporter
{
    public string Export(Invoice invoice, string format)
    {
        // ❌ Violates OCP — must edit this class for every new format
        switch (format)
        {
            case "PDF":
                return ExportPdf(invoice);
            case "Excel":
                return ExportExcel(invoice);
            case "CSV":
                return ExportCsv(invoice);
            default:
                throw new NotSupportedException(format);
        }
    }
}
// Adding JSON export → modify InvoiceExporter again

Fix — extend via new classes, not edits

public interface IInvoiceExporter
{
    string Format { get; }
    string Export(Invoice invoice);
}

public class PdfInvoiceExporter : IInvoiceExporter
{
    public string Format => "PDF";
    public string Export(Invoice invoice) => /* PDF logic */;
}

public class ExcelInvoiceExporter : IInvoiceExporter { ... }

public class InvoiceExportService
{
    private readonly IEnumerable<IInvoiceExporter> _exporters;
    public InvoiceExportService(IEnumerable<IInvoiceExporter> exporters)
        => _exporters = exporters;

    public string Export(Invoice invoice, string format) =>
        _exporters.First(e => e.Format == format).Export(invoice);
}

// New JSON exporter — new class + DI registration only
public class JsonInvoiceExporter : IInvoiceExporter { ... }

Signs you are violating OCP

  • Long if/switch on type or string codes that keeps growing.
  • Every new feature requires changing a central "god" class.
  • Merge conflicts in the same file when multiple teams add variants.

Interview Answer

OCP means I extend behavior with new classes or strategies instead of modifying existing ones. A switch on payment or export type that we edit for every new option violates OCP; replacing it with an interface and DI-registered implementations lets me add JSON or Cash payment without touching core billing code.

Caching — Why Use It? Memory vs Redis

Caching stores frequently read data closer to the application to reduce latency, database load, and cost. Use it when reads dominate, data changes infrequently, or recomputing is expensive.

Why cache?

  • Faster API responses — avoid repeated DB/API calls.
  • Lower database pressure — fewer identical queries under load.
  • Better scalability — serve hot data from memory instead of SQL.
  • Cost savings — fewer DTU/RU on cloud databases.

IMemoryCache vs Redis (IDistributedCache)

IMemoryCacheRedis (distributed)
ScopeSingle server / processShared across all app instances
SpeedFastest — in-process RAMNetwork hop — still very fast
Survives restart?NoYes (with persistence config)
Use whenSingle-node dev/small appApp Service scale-out, multiple pods
ConsistencyEach node has own copyAll nodes see same cache
// In-memory — single instance
_cache.Set("product:42", product, TimeSpan.FromMinutes(5));

// Redis — multi-instance
await _distributedCache.SetStringAsync(
    "product:42",
    JsonSerializer.Serialize(product),
    new DistributedCacheEntryOptions
    {
        AbsoluteExpirationRelativeToNow = TimeSpan.FromMinutes(5)
    });

// Cache-aside pattern
if (!_cache.TryGetValue(key, out Product? p))
{
    p = await _db.Products.FindAsync(id);
    _cache.Set(key, p, TimeSpan.FromMinutes(10));
}

When NOT to cache

  • Data must be real-time accurate (account balance without invalidation).
  • Highly personalized or unique per-request data with no reuse.
  • Without a clear TTL or invalidation strategy on writes.

Interview Answer

I cache to cut latency and database load on hot reads using cache-aside with TTLs. IMemoryCache is fine for a single server; when the API scales to multiple instances I use Redis via IDistributedCache so all nodes share the same cache. I invalidate or update cache entries when underlying data changes.

CTE — What Is It? Have You Used It?

A Common Table Expression (CTE) is a named temporary result set defined with WITH, used in a single SELECT/INSERT/UPDATE/DELETE statement. It makes complex queries readable and supports recursion.

WITH ActiveEmployees AS (
    SELECT EmployeeId, Name, DeptId, Salary
    FROM Employees
    WHERE IsActive = 1
),
DeptAvg AS (
    SELECT DeptId, AVG(Salary) AS AvgSalary
    FROM ActiveEmployees
    GROUP BY DeptId
)
SELECT e.Name, e.Salary, d.AvgSalary

Transaction in SQL — What It Is & How to Implement

A transaction groups one or more SQL statements into one atomic unit: all succeed (COMMIT) or all undo (ROLLBACK).

How to implement (T-SQL)

SET XACT_ABORT ON;
BEGIN TRANSACTION;

BEGIN TRY
    INSERT INTO Orders (CustomerId, Total)
    VALUES (101, 250.00);

    INSERT INTO OrderLines (OrderId, ProductId, Qty)
    VALUES (SCOPE_IDENTITY(), 5, 2);

    UPDATE Inventory SET Qty = Qty - 2 WHERE ProductId = 5;

    COMMIT TRANSACTION;
END TRY
BEGIN CATCH
    IF @@TRANCOUNT > 0
        ROLLBACK TRANSACTION;
    THROW;
END CATCH;

In application code (ADO.NET)

await using var tx = await connection.BeginTransactionAsync();
try
{
    await cmd1.ExecuteNonQueryAsync();
    await cmd2.ExecuteNonQueryAsync();
    await tx.CommitAsync();
}
catch
{
    await tx.RollbackAsync();
    throw;
}

Key rules

  • Keep transactions short to reduce locking and deadlocks.
  • Use TRY/CATCH + check @@TRANCOUNT so failures always roll back.
  • One business operation = one transaction boundary when possible.

Interview Answer

I wrap related DML in BEGIN TRANSACTION, commit on success, and roll back on any error using TRY/CATCH. In .NET I use explicit transactions on the connection or EF SaveChanges inside a transaction so related rows stay consistent.

What Is a Transaction in SQL? (Not “Transition”)

In interviews, “Transition” usually means Transaction — a logical unit of work where one or more SQL statements succeed or fail together.

A transaction groups operations so the database stays consistent: either all changes are applied, or none are (after ROLLBACK).

BEGIN TRANSACTION;

UPDATE Accounts SET Balance = Balance - 1000 WHERE AccountId = 1;
UPDATE Accounts SET Balance = Balance + 1000 WHERE AccountId = 2;

-- If both succeed:
COMMIT TRANSACTION;

-- If any step fails:
ROLLBACK TRANSACTION;

Why transactions matter

  • Money transfer — debit and credit must both happen or neither.
  • Order + order lines — header and details inserted atomically.
  • Batch imports — 500 rows: all valid rows commit together or roll back on failure (depending on design).

Transaction boundaries

Start with BEGIN TRAN (or implicit transaction), end with COMMIT (save) or ROLLBACK (undo). SQL Server follows ACID properties for transactional work.

Interview Answer

A transaction is a group of SQL operations treated as one unit. If any part fails, I roll back so the database is not left half-updated. I use explicit transactions for financial transfers, multi-table inserts, and batch jobs where consistency is critical.

ACID means transactions are Atomic (all-or-nothing), Consistent (rules enforced), Isolated (controlled concurrency), and Durable (committed data survives failure). SQL Server implements this through the transaction log, locks/row versioning, and constraints.

By operation

  • DELETE — only deleted has rows.

Transaction Scenario — Partial Insert of 500 Records

Scenario: Insert 500 rows into a staging table and a main table. Row 300 fails (constraint violation). What happens depends on how you handle the transaction.

Option 1 — Single transaction (all or nothing)

SET XACT_ABORT ON;
BEGIN TRANSACTION;

BEGIN TRY
    INSERT INTO Staging (Col1, Col2)
    SELECT Col1, Col2 FROM @BulkData;  -- 500 rows

    INSERT INTO MainTable (Col1, Col2)
    SELECT Col1, Col2 FROM Staging;

    COMMIT TRANSACTION;
    -- All 500 committed only if every statement succeeds
END TRY
BEGIN CATCH
    ROLLBACK TRANSACTION;
    -- Row 300 failure → entire batch undone
    THROW;
END CATCH;

Result: Failure at row 300 → ROLLBACK → zero rows in MainTable (and Staging if in same tran).

Option 2 — Row-by-row with savepoints (partial success)

BEGIN TRANSACTION;

DECLARE @i INT = 1;
WHILE @i <= 500
BEGIN
    SAVE TRANSACTION sp_row;

    BEGIN TRY
        INSERT INTO MainTable (...) VALUES (...);  -- one row
        COMMIT TRANSACTION sp_row;  -- not valid — use nested or per-row tran
    END TRY
    BEGIN CATCH
        ROLLBACK TRANSACTION sp_row;
        -- log error row, continue
    END CATCH;

    SET @i += 1;
END;

COMMIT TRANSACTION;

Often implemented as separate small transactions per row or batch of 50 with error logging — 499 succeed, 1 fails.

Option 3 — Set-based with validation first (recommended)

BEGIN TRAN;
    INSERT INTO Staging SELECT * FROM @BulkData;

    -- Reject batch if any invalid
    IF EXISTS (SELECT 1 FROM Staging WHERE Col1 IS NULL)
        THROW 50000, 'Invalid rows in batch', 1;

    INSERT INTO MainTable SELECT * FROM Staging WHERE IsValid = 1;
COMMIT;

Interview Answer

With one BEGIN TRAN around all 500 inserts, a failure at row 300 causes ROLLBACK and none of the rows persist. If the business needs partial success, I use per-row or batched transactions with error logging, or validate the full set in staging before a single COMMIT. I always clarify requirements: all-or-nothing vs best-effort import.

COMMIT and ROLLBACK in SQL Server

COMMIT makes all changes in the current transaction permanent. ROLLBACK undoes all changes since the last BEGIN TRANSACTION.

CommandEffect

ROLLBACK / ROLLBACK TRANSACTIONUndo all changes in the transaction
SAVE TRANSACTION nameSavepoint within a transaction (partial rollback)

Modern pattern — TRY/CATCH + XACT_ABORT

SET XACT_ABORT ON;
BEGIN TRANSACTION;

BEGIN TRY
    INSERT INTO Orders (...) VALUES (...);
    INSERT INTO OrderLines (...) VALUES (...);
    COMMIT TRANSACTION;
END TRY
BEGIN CATCH
    IF @@TRANCOUNT > 0
        ROLLBACK TRANSACTION;

    DECLARE @msg NVARCHAR(4000) = ERROR_MESSAGE();
    RAISERROR(@msg, 16, 1);
END CATCH;

Key Points

  • @@TRANCOUNT — number of open transactions; ROLLBACK all if > 0 in CATCH.
  • Uncommitted changes are visible only within the session (depending on isolation).
  • XACT_ABORT ON auto-rolls back on runtime errors.

Interview Answer

COMMIT persists everything since BEGIN TRAN; ROLLBACK reverses it. I wrap related DML in TRY/CATCH, check @@TRANCOUNT, and ROLLBACK on failure so the database never ends up half-updated. SAVE TRANSACTION allows rolling back to a savepoint without aborting the whole batch.

How Many Clustered Indexes per Table?

In SQL Server, a table can have at most one clustered index. The clustered index defines the physical sort order of the data rows (or is the table itself).

Rules

  • 0 clustered indexes — table is a heap (unordered storage).
  • 1 clustered index — normal case; often on PRIMARY KEY.
  • 2+ clustered indexes — not allowed on one table.
-- One clustered index (typical)
CREATE TABLE Employees (
    EmployeeId INT PRIMARY KEY CLUSTERED,  -- clustered index on PK
    Name NVARCHAR(100),
    DeptId INT
);

-- Many NON-clustered indexes allowed
CREATE NONCLUSTERED INDEX IX_Emp_Dept ON Employees(DeptId);
CREATE NONCLUSTERED INDEX IX_Emp_Name ON Employees(Name);

Heap vs clustered

StorageClustered index
HeapNo clustered index — rows stored in insertion order
Clustered tableOne clustered index — leaf level = data pages

You can have many non-clustered indexes (up to 999 on older versions, 999 nonclustered + 1 clustered in practice). Non-clustered leaf nodes point to the clustered key or RID (heap).

Interview Answer

Only one clustered index per table because it controls physical row order. You can have zero (heap) or one (usually on the primary key). Non-clustered indexes are unlimited in practice and are separate structures that reference the clustered key or row identifier.

Window Functions in SQL Server

Window functions perform calculations across a set of rows related to the current row without collapsing rows into groups (unlike GROUP BY). They use OVER (PARTITION BY ... ORDER BY ...).

Common window functions

FunctionPurpose
ROW_NUMBER()Unique sequential number per partition (ties get different numbers)
RANK()Rank with gaps after ties (1, 1, 3)
DENSE_RANK()Rank without gaps (1, 1, 2)
NTILE(n)Divide rows into n buckets
LAG / LEADPrevious / next row value
SUM / AVG / COUNT OVERRunning or partition totals (analytics)
SELECT
    EmployeeId,
    Name,
    DeptId,
    Salary,
    ROW_NUMBER() OVER (PARTITION BY DeptId ORDER BY Salary DESC) AS RowNum,
    RANK()       OVER (PARTITION BY DeptId ORDER BY Salary DESC) AS SalaryRank,
    DENSE_RANK() OVER (PARTITION BY DeptId ORDER BY Salary DESC) AS DenseRank,
    SUM(Salary)  OVER (PARTITION BY DeptId) AS DeptTotal
FROM Employees;

Window vs GROUP BY

-- GROUP BY — one row per dept
SELECT DeptId, AVG(Salary) FROM Employees GROUP BY DeptId;

-- Window — keeps every employee row, adds dept average
SELECT Name, Salary,
       AVG(Salary) OVER (PARTITION BY DeptId) AS DeptAvg
FROM Employees;

Important rules

  • Cannot use window functions directly in WHERE — wrap in CTE/subquery and filter outside.
  • PARTITION BY is optional (whole result set is one partition).
  • ORDER BY in OVER defines ranking and running calculations.

RANK vs DENSE_RANK (quick reference)

Interview Answer

Window functions compute over a row set defined by OVER without grouping rows away. I use ROW_NUMBER for top-N and pagination, RANK/DENSE_RANK for leaderboards, and SUM/AVG OVER for running totals. I filter results in an outer query or CTE because OVER cannot go in WHERE.

SELECT * INTO — WHERE 1 = 0 vs WHERE 1 = 1

SELECT * INTO creates a new table and populates it from a query. The WHERE clause controls whether rows are copied; the column structure always comes from the source query.

1) WHERE 1 = 0 — structure only, no data

SELECT * INTO NewTable FROM OldTable WHERE 1 = 0;

What happens:

  • Creates NewTable with the same columns and data types as OldTable.
  • Copies zero rows (condition is always false).
  • Table is empty but ready for INSERT/ETL.

2) WHERE 1 = 1 — structure + all data

SELECT * INTO NewTable FROM OldTable WHERE 1 = 1;

What happens:

  • Creates NewTable with the same columns and types.
  • Copies every row from OldTable (condition is always true).
  • Equivalent to a full table copy in one statement.

Side-by-side

WHERE 1 = 0WHERE 1 = 1
Rows copied0All rows
Schema copiedYes (columns, types)Yes
Indexes / PK / FK / constraintsNot copied — only columns
Triggers / defaultsNot copied

What is NOT copied (both cases)

SELECT INTO does not copy indexes, primary keys, foreign keys, constraints, triggers, or extended properties. You get a heap-like new table with data (or empty). Add indexes/constraints afterward if needed.

Temp table variant

-- Empty temp table with same shape as source
SELECT * INTO #Staging FROM dbo.Orders WHERE 1 = 0;

-- Full copy into temp table (session-scoped)
SELECT * INTO #OrdersBackup FROM dbo.Orders WHERE 1 = 1;

Real-time use cases

PatternUse case
WHERE 1 = 0Quickly clone table structure for staging, migration scripts, or empty sandbox tables
WHERE 1 = 0ETL: create target shell, then INSERT INTO NewTable SELECT ... with transforms
WHERE 1 = 0Create temp table matching production columns before bulk load
WHERE 1 = 1One-shot backup/snapshot of a table before risky UPDATE/DELETE
WHERE 1 = 1Copy production subset to reporting DB (often with a real filter instead of 1=1)
WHERE 1 = 1Archive historical data: SELECT * INTO Archive2024 FROM Orders WHERE OrderDate >= '2024-01-01'
-- Real example: backup before mass update
SELECT * INTO Orders_Backup_20250602 FROM Orders WHERE 1 = 1;
UPDATE Orders SET Status = 'Closed' WHERE OrderDate < '2020-01-01';

-- Real example: staging table for import
SELECT * INTO dbo.Customer_Staging FROM dbo.Customer WHERE 1 = 0;
BULK INSERT dbo.Customer_Staging FROM 'file.csv' ...;

Modern alternatives

  • SELECT TOP 0 * INTO ... — same effect as WHERE 1 = 0.
  • CREATE TABLE ... AS SELECT — not in SQL Server; use SELECT INTO or CREATE TABLE + INSERT.
  • For schema only: Script Table as CREATE in SSMS, or CREATE TABLE ... LIKE (other databases).

Interview Answer

WHERE 1 = 0 creates a new table with the same columns but no rows — I use it to clone structure for staging or migrations. WHERE 1 = 1 creates the table and copies all rows — I use it for quick backups or snapshots before destructive changes. Neither copies indexes or constraints; only column definitions and optionally data.

Pagination in SQL Server

Pagination returns one page of rows at a time (e.g. page 2, 10 rows per page) instead of loading the entire table.

OFFSET / FETCH (SQL Server 2012+) — recommended

DECLARE @PageNumber INT = 2;   -- 2nd page
DECLARE @PageSize     INT = 10;

SELECT EmployeeId, Name, DeptId
FROM Employees
ORDER BY EmployeeId   -- stable sort required
OFFSET (@PageNumber - 1) * @PageSize ROWS
FETCH NEXT @PageSize ROWS ONLY;

Page 1 → OFFSET 0, Page 2 → OFFSET 10, etc.

Total count for UI (optional)

SELECT COUNT(*) AS TotalRows FROM Employees;

-- Or window function in one query (heavier on large tables)
SELECT *, COUNT(*) OVER() AS TotalRows
FROM Employees
ORDER BY EmployeeId
OFFSET 10 ROWS FETCH NEXT 10 ROWS ONLY;

Legacy: ROW_NUMBER()

SELECT EmployeeId, Name
FROM (
    SELECT *,
           ROW_NUMBER() OVER (ORDER BY EmployeeId) AS rn
    FROM Employees
) t
WHERE rn BETWEEN 11 AND 20;  -- page 2, size 10

Key Points

  • Always ORDER BY — without it, page order is undefined.
  • Large OFFSET on huge tables can be slow (skips many rows); keyset pagination is better for deep pages.
  • API pattern: pass page and pageSize as parameters to a stored procedure.

Interview Answer

I paginate with ORDER BY plus OFFSET/FETCH: OFFSET (page-1)*pageSize ROWS FETCH NEXT pageSize ROWS ONLY. I return total count separately for the UI and use a stable sort column like primary key.

               PARTITION BY Email        -- duplicate rule

           ROW_NUMBER() OVER (
               PARTITION BY Email
               ORDER BY UserID

    FROM dbo.[User]

How Can We Optimize Query Performance?

Optimize using measurement first (execution plan, duration, IO), then apply targeted fixes.

1. Find the bottleneck

  • Enable actual execution plan in SSMS.
  • Look for table/clustered index scans, high cost %, missing index hints.
  • Check SET STATISTICS IO, TIME ON for logical reads and elapsed time.

2. Indexing

  • Add nonclustered indexes on WHERE, JOIN, and ORDER BY columns.
  • Use covering indexes (INCLUDE columns) to avoid key lookups.
  • Remove unused/redundant indexes that slow writes.
  • Update statistics (UPDATE STATISTICS or automatic).

3. Write better SQL

  • Avoid SELECT * — return only needed columns.
  • Filter early; avoid functions on indexed columns in WHERE (WHERE YEAR(d)=2024 → range on d).
  • Replace correlated subqueries with JOINs or window functions when plans are bad.
  • Use EXISTS instead of IN for large subqueries when appropriate.
  • Paginate large results — do not return millions of rows.

4. Server & design

  • Fix implicit conversions (NVARCHAR column vs VARCHAR parameter).
  • Reduce blocking — shorter transactions, right isolation level.
  • Partition very large tables; archive old data.
  • Warm cache for critical reports; use read replicas for reporting.
-- Bad — non-sargable
WHERE YEAR(OrderDate) = 2024

-- Better — sargable range
WHERE OrderDate >= '2024-01-01' AND OrderDate < '2025-01-01';

Checklist

SymptomTypical fix

Key lookup high costCovering index with INCLUDE
Bad cardinality estimateUpdate stats, recompile, fix parameter sniffing
Too many rows returnedFilter, paginate, project fewer columns

Interview Answer

I start with the execution plan and missing-index suggestions, then add or tune indexes on filter and join columns, avoid SELECT * and non-sargable predicates, and keep statistics current. I measure before and after each change rather than adding indexes blindly.

What Are Joins? What Is a Self Join?

A JOIN combines rows from two or more tables based on a related column (usually primary key = foreign key).

Types of joins

JoinResult
INNER JOINOnly matching rows from both tables
LEFT JOIN (LEFT OUTER)All rows from left table + matches from right (NULL if no match)
RIGHT JOINAll rows from right + matches from left
FULL OUTER JOINAll rows from both; NULL where no match

-- INNER JOIN — employees with department names
SELECT e.Name, d.DeptName
FROM Employees e
INNER JOIN Departments d ON e.DeptId = d.DeptId;

-- LEFT JOIN — all employees, even without department
SELECT e.Name, d.DeptName
FROM Employees e
LEFT JOIN Departments d ON e.DeptId = d.DeptId;

Self join

A self join joins a table to itself — useful for hierarchies (employee → manager) or comparing rows in the same table.

-- Employee and their manager name (same table, two aliases)
SELECT
    e.Name AS Employee,
    m.Name AS Manager
FROM Employees e
LEFT JOIN Employees m ON e.ManagerId = m.EmployeeId;

-- Pairs in same department (excluding self)
SELECT a.Name, b.Name
FROM Employees a
INNER JOIN Employees b
    ON a.DeptId = b.DeptId AND a.EmployeeId < b.EmployeeId;

Interview Answer

Joins combine tables on related keys — INNER for matches only, LEFT when you need all rows from the driving table. A self join uses two aliases on the same table, commonly for manager-employee hierarchy or intra-table comparisons.

Use of Clustered and Non-Clustered Indexes

Indexes speed up reads (SELECT, JOIN, WHERE, ORDER BY) at the cost of slower writes (INSERT/UPDATE/DELETE) and extra storage.

Clustered index — when to use

  • One per table — defines physical row order.
  • Put on the column used most for range scans and sorting — often PRIMARY KEY (identity).
  • Good for: WHERE OrderDate BETWEEN ..., ORDER BY OrderId, sequential inserts on ID.
  • Avoid wide, random clustered keys (e.g. GUID) — causes page splits and fragmentation.

Non-clustered index — when to use

  • Add on columns in WHERE, JOIN, and ORDER BY that are not the clustered key.
  • Covering index — INCLUDE extra columns so the query is satisfied from the index alone (no key lookup).
  • Foreign keys and highly selective filters (Status, Email, CustomerId).
  • Many allowed per table; do not over-index every column — hurts insert/update throughput.
ScenarioIndex choice
Primary key, sequential IDClustered on PK
Search by emailNonclustered on Email (often UNIQUE)
Report filter + return few columnsNonclustered with INCLUDE
Heap table (no clustered)Nonclustered leaf points to RID
CREATE CLUSTERED INDEX IX_Order_Date ON Orders(OrderDate);

CREATE NONCLUSTERED INDEX IX_Order_Customer
ON Orders(CustomerId)
INCLUDE (OrderDate, Total);  -- covering for common query

Interview Answer

I use the clustered index for the main access path—usually the PK—for physical ordering. I add nonclustered indexes on filter and join columns and covering indexes when plans show expensive key lookups. I balance read speed with write overhead and validate with execution plans.

SQL Server Optimization Techniques (5–7 Ways)

Top techniques I use to improve SQL Server performance — always measure first (plan, duration, IO), then apply fixes.

  1. Proper indexing — nonclustered indexes on WHERE/JOIN/ORDER BY; covering indexes with INCLUDE; one sensible clustered key (often PK).
  2. Update statistics — keep optimizer estimates accurate (UPDATE STATISTICS, auto stats, Query Store for regressions).
  3. Rewrite inefficient SQL — avoid SELECT *, non-sargable functions on columns, correlated subqueries; use EXISTS/JOINs and filter early.
  4. Read execution plans — fix scans, key lookups, implicit conversions, bad joins; use missing-index hints as starting points only.
  5. Reduce locking & blocking — shorter transactions, right isolation level, READ COMMITTED SNAPSHOT where appropriate.
  6. Partition & archive data — smaller hot working set, partition large tables by date, move history to archive tables.
  7. Hardware & configuration — enough memory for buffer pool, fast disks for log/data, MAXDOP/Cost Threshold for Parallelism tuned for workload.

Bonus techniques

  • Parameterized queries / avoid plan cache pollution.
  • Tempdb tuning for heavy sorts/hashes.
  • Caching at app layer (Redis) for read-heavy reference data.

Interview Answer

I list indexing, current statistics, query rewrites, plan analysis, shorter transactions, data archiving, and server tuning as my main levers. I pick based on what the plan and IO stats show—not by adding indexes everywhere.

Find 5th Highest Rank Using RANK and CTE

Use a CTE with RANK() (or DENSE_RANK() if you want 5th distinct value without gaps) over salaries, then filter rnk = 5.

Using RANK (gaps after ties — Olympic style)

WITH SalaryRank AS (
    SELECT
        EmployeeId,
        Name,
        Salary,
        RANK() OVER (ORDER BY Salary DESC) AS rnk
    FROM Employees
)
SELECT EmployeeId, Name, Salary, rnk
FROM SalaryRank
WHERE rnk = 5;

If two employees tie for 4th, next rank is 6 — so rnk = 5 may return no rows.

Using DENSE_RANK (no gaps — 5th distinct salary)

WITH SalaryRank AS (
    SELECT
        EmployeeId,
        Name,
        Salary,
        DENSE_RANK() OVER (ORDER BY Salary DESC) AS drnk
    FROM Employees
)
SELECT EmployeeId, Name, Salary, drnk
FROM SalaryRank
WHERE drnk = 5;

Return only the 5th highest salary value

WITH DistinctSalaries AS (
    SELECT DISTINCT Salary,
           DENSE_RANK() OVER (ORDER BY Salary DESC) AS drnk
    FROM Employees
)
SELECT Salary AS FifthHighestSalary
FROM DistinctSalaries
WHERE drnk = 5;

Interview Answer

I wrap the table in a CTE, apply RANK or DENSE_RANK over ORDER BY Salary DESC, and SELECT WHERE rank = 5. I clarify whether ties should skip ranks (RANK) or not (DENSE_RANK) before choosing the function.

Two Users Update Same Data — Who Was First?

When two people edit the same row, the first COMMIT wins. The second update must detect that data changed and return a friendly “already updated” message — not overwrite silently.

Pattern: rowversion / timestamp token

CREATE TABLE Orders (
    OrderId    INT PRIMARY KEY,
    Status     NVARCHAR(20),
    Amount     DECIMAL(18,2),
    RowVer     ROWVERSION   -- auto-updates on every change
);

-- User A reads at 10:00
SELECT OrderId, Status, Amount, RowVer FROM Orders WHERE OrderId = 1;
-- RowVer = 0x00000000000007D1

-- User B reads same row, updates first at 10:01 — succeeds
UPDATE Orders SET Status = 'Shipped', Amount = 500
WHERE OrderId = 1;
-- RowVer changes to 0x00000000000007D2

-- User A tries at 10:02 with OLD RowVer — must fail
UPDATE Orders
SET Status = 'Approved', Amount = 450
WHERE OrderId = 1 AND RowVer = 0x00000000000007D1;
-- @@ROWCOUNT = 0 → someone else updated first

Application logic (.NET / API)

// On save, include original RowVer from when user opened the form
var rows = await _db.Database.ExecuteSqlRawAsync(
    @"UPDATE Orders SET Status = {0}, Amount = {1}
      WHERE OrderId = {2} AND RowVer = {3}",
    status, amount, orderId, originalRowVer);

if (rows == 0)
    return Conflict("Sorry, this record was already updated by another user. Please refresh.");

How you know who was first

  • First commit succeeds and bumps ROWVERSION / LastModifiedUtc.
  • Second update affects 0 rows when WHERE includes old token → tell user to refresh.
  • Optional audit table: UpdatedBy, UpdatedAt shows who won.

Interview Answer

I store a concurrency token (ROWVERSION or LastModified). On update, the WHERE clause includes the token the user read. If no rows updated, the second person gets a 409 Conflict message to refresh — the first commit already changed the row.

Optimistic Concurrency — What It Is & How to Use It

Optimistic concurrency assumes conflicts are rare: users read data without long locks; at save time the app checks whether the row still matches what they read. If not, the update fails and the user refreshes.

Optimistic vs pessimistic

OptimisticPessimistic
Locks while reading?No — read freelyYes — UPDLOCK, HOLDLOCK
Conflict detectionAt UPDATE (token / version)Blocked until lock released
Best forWeb apps, low collision rateHigh contention, banking counters

How to implement in SQL Server

  1. Add ROWVERSION column (or LastModified datetime + user id).
  2. Client reads row including token when opening edit screen.
  3. On UPDATE/DELETE, include token in WHERE: WHERE Id = @id AND RowVer = @oldVer.
  4. If @@ROWCOUNT = 0, throw concurrency exception → “Data was modified by another user.”
UPDATE Products
SET Name = @name, Price = @price
WHERE ProductId = @id AND RowVer = @rowVerFromClient;

IF @@ROWCOUNT = 0
    RAISERROR('Concurrency conflict', 16, 1);
